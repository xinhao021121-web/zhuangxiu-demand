# 问需 · 解读（桌面工作台）

公司内部工具，出门前在电脑上把量房沟通清单做出来：**导入 → 确认外发 → 看理解 → 筛清单 → 导出**（F1–F6）；
量房回来在这里收口：**改名 → 补一条遗漏 → 看四张回流报表**（R2）。

## 起服务

```bash
pnpm install --dir studio --ignore-workspace   # 依赖按包安装，不动仓库根目录
pnpm run studio:dev                            # http://127.0.0.1:3000（另起一个终端跑 pnpm run api:dev）
```

登录用种子账号：手机号 `13800000002`，验证码 `000000`。

## 与 API 的分工

浏览器不算业务结论，也不碰模型密钥：清单判据、合并、排序、脱敏全在 `packages/*`，服务端在 `services/api`。
`/api/*` 由 Next 的 rewrite 代理到 API 服务（默认 `http://127.0.0.1:8787`，用 `API_BASE` 改）。

前端用到的领域包只有两处，都是纯函数：导出 Markdown（`@zx/checklist`）与字段标签（`@zx/field-spec`）。

## 回流（R2）

| 动作 | 接口 | 说明 |
| --- | --- | --- |
| 改名 | `PATCH /demand-sheets/{id}` | 采集端不收集房主姓名，房主提交的那份落库叫「未命名需求单」，由设计师改成认得出的叫法；只动名字，房主填的内容一个字不变 |
| 遗漏补录 | `POST /demand-sheets/{id}/omissions` | 清单页底部补一句「这次该问但没列的是……」，要选分区与归类；落成一条 `omission_log` 事件，只追加、不回溯改历史 |
| 回流报表 | `GET /reports` | 规则 / 判据 / 字段三张健康度 + 遗漏台账。汇总逻辑不在这层，在 `@zx/service` 的 `buildReports`（技术方案 6.12）——所以演示模式与真实服务用的是同一份口径 |

报表里两种「不是 0」的写法值得注意：分母为 0 显示「—（还没有样本）」，没有来源的列显示「未采集」——
一个假的 0 比空着更糟（产品文档第十章）。

## 导入（F1）

左侧「需求单」旁有一个「导入」：选一份采集端导出的 JSON，或者直接把 JSON 粘进去，
再写一个认得出的叫法（可以留空，房主端不收集姓名）。

校验用的是契约本身（`DemandSheetImportSchema`）：粘错、缺一块，当场说清是哪一处不对，不用等一次往返；
服务端仍然会再校验一次——两边认的是同一份 schema。导入来的来源一律记 `file`，与房主端提交那条路分开记。

## 关于依赖选择

技术方案里的状态层是 Zustand + TanStack Query。这一版直接用 React 自带的 state 与 fetch：
工作台只有十几个接口、没有跨页共享状态，引入缓存层只会多一层要维护的东西。
真要做服务端渲染的分享页时再补，不影响现在的结构。
