## 一、结论先说

1. **单份解读约 2 分钱**（实测 2085 输入 token + 2473 输出 token，按示例单价折算），占装修客单价的十万分之一量级。
2. **所以成本不是这个产品的约束。** 盈亏平衡的门槛低到「只要让返工率下降万分之零点几」就回本——这个门槛事实上不存在。
3. **真正决定它值不值得做的，是「遗漏率能降多少」，而那个数字现在还没有。** 所以正确的动作不是省 token，而是把质量与遗漏测准。

这条结论反过来支持了前面几个设计决定：**不设条数上限、宁可多给几条让设计师删、规则托底宁可多一条**——每条多花的是几厘钱，而漏一条的代价是几千块。

## 二、成本侧（已实测）

### 2.1 实测数据

来自 `pnpm run eval:model` 的成本实测（13 个用例各一次，共 14 次调用——有 1 次重试）：

| 项 | 实测值 |
| --- | --- |
| 输入 token | 合计 29189 · **单次均值 2085** |
| 输出 token | 合计 34616 · **单次均值 2473** |
| 前缀缓存命中 | 26240 / 29189 = **90%** |
| 调用次数 | 14 次 / 13 个用例 = **1.08 次/份** |
| 单份耗时 | 约 11 秒（两批各 39 次调用：419.7s、435.0s） |

### 2.2 单份成本怎么算

```
单份解读成本
  = 输入 token × (1 − 缓存命中率) × 输入单价
  + 输入 token × 缓存命中率 × 缓存单价
  + 输出 token × 输出单价
```

把实测值代进去（输入 2085、输出 2473、命中率 90%）：

```
≈ 208.5 token × 输入单价 + 1876.5 token × 缓存单价 + 2473 token × 输出单价
```

**单价不写死在文档里**——官方会调价，写死就把这份模型写过期了。用之前按官网公示价填三个数：

| 情景 | 输入单价 | 缓存单价 | 输出单价 | 单份成本 |
| --- | --- | --- | --- | --- |
| 示例价 A | ¥2 / 百万 token | ¥0.5 / 百万 | ¥8 / 百万 | **≈ ¥0.021** |
| 示例价 B（贵 5 倍） | ¥10 / 百万 | ¥2 / 百万 | ¥40 / 百万 | **≈ ¥0.105** |

两行都是**占位数字，用之前按官网核对**。留示例价 B 是为了看结论抗不抗涨价：单价涨 5 倍，单份成本才从 2 分钱变成 1 毛钱。

### 2.3 成本结构：钱花在哪

| 项 | 占比 | 含义 |
| --- | --- | --- |
| 输出 token | **≈ 94%** | 钱几乎全花在「模型写出来的那份清单」上 |
| 输入 token | ≈ 6% | 其中 90% 还命中前缀缓存，实际负担更小 |

两个直接推论：

- **唯一有效的省钱动作是让模型少输出**，而输出就是清单本身。任何「压缩输出」的手段都在削清单，与「宁可多给几条让设计师删」直接冲突——这条冲突要明确站在清单这一边。
- **前缀缓存做对了，但它省下的钱本来就不重要**（输入只占 6%）。它的价值在别处：固定前缀让提示词稳定、让改动可复测。别为了缓存再加复杂机制。

### 2.4 固定成本（估算，不是实测）

这部分没有实测数据，列成清单等公司口径填：

| 项 | 说明 |
| --- | --- |
| 服务器 | 一个境内云主机 + Postgres + 对象存储，量小 |
| 域名与备案 | 只在走公网时才需要；接受内网使用可省（技术方案 9.2） |
| 模型密钥 | 按量计费，即上面的单份成本 |
| **人力** | 规则表维护、判据调优、访谈与落地培训——**这才是主要投入**，见第六节 |

## 三、收益侧（参数待访谈填）

收益不写假设值，只列参数与它的来源。每个参数都能在《用户研究方案》里找到对应的问题——**这张表就是那份方案的产出清单**。

| 参数 | 符号 | 当前值 | 从哪来 |
| --- | --- | --- | --- |
| 一次返工或增项的成本 | `R` | 待填 | 访谈 Q3 追问的「多花了多少时间、多少钱」；公司可补历史增项数据 |
| 当前因需求遗漏导致的返工率 | `p` | 待填 | 访谈 Q3 + 公司项目数据 |
| 工具能把返工率降多少 | `Δp` | 待填 | **试点后才知道**，见第五节 |
| 每份需求单节省的设计师时间 | `T` | 待填 | 访谈 Q5（现场做法还原）与 Q8（房主卡点） |
| 设计师时薪 | `W` | 待填 | 公司 |
| 月处理量 | `N` | 待填 | 公司（设计师人数 × 人均月客户数） |

```
收益 = R × Δp × N + T × W ÷ 60 × N
```

前一项是少掉的返工，后一项是省下的时间。

---

## 四、盈亏平衡

```
每份成本 = 单份模型成本 × 1.08（实测的重新生成系数） + 固定成本 ÷ N
每份收益 = R × Δp + T × W ÷ 60

回本条件：R × Δp + T × W ÷ 60 ≥ 每份成本
```

先忽略时间节省（把它当额外收益），只问「返工率要降多少才回本」：

```
Δp* = 每份成本 ÷ R
```

代入示例价 A，再假设一次返工成本 `R = ¥3000`（**这个数只是用来演示公式，真实值等访谈**）：

```
Δp* = 0.021 ÷ 3000 ≈ 0.0007%
```

**万分之一都不到。** 就算把返工成本压到 `R = ¥300`，门槛也只有万分之七；把单价按示例价 B 涨 5 倍，门槛依然是万分之三点五。

结论：**在任何一个像样的假设下，回本门槛都不构成约束。**

## 五、敏感性：对什么不敏感、对什么敏感

| 变量 | 变化 10 倍，结论会翻吗 |
| --- | --- |
| 模型单价 | 不会。单份成本从 2 分到 2 毛，回本门槛仍在万分之一量级 |
| token 用量 | 不会。需求单再厚，量级不变 |
| 调用次数（重新生成） | 不会，除非重新生成上百次 |
| 一次返工的成本 `R` | **也不会**——除非返工几乎不花钱（`R` 小于几块钱），而那与装修行业的常识不符 |
| **返工率降幅 `Δp`** | **会**。这是唯一能决定结论的变量，而它只有试点能给 |

**所以这份模型最脆的地方不是成本，是收益。**

## 六、真正的投入在哪

把模型成本算清楚之后，投入清单反而更清楚：

1. **人力**：规则表（72 条）与清单判据的持续调优、回流闭环的定期看数（产品文档第七章的四张报表）。这是唯一会持续发生的大头。
2. **流程**：两个设计师端要真的接进「出门前 → 现场」的动线，否则清单生成出来也没人用。
3. **评测**：每次改提示词或换型号要复跑真机实测。实测下来这部分的钱可以忽略——到目前为止整个评测累计约 130 次调用，按示例价 A 折算不到 ¥3。

第 3 条值得单独说：**做 AI 功能，把质量测准这件事本身很便宜，不做才是贵的。** 前面 BC-03 那次「养猫三次全漏」如果没有评测体系，只会以「某次量房忘了问猫砂盆」的形式沉到现场里去。

## 七、这份模型不测什么

- **不测收益**，只给出算收益需要的参数与公式；参数必须由访谈与试点填。
- **不测归因**：返工减少可能来自设计师更仔细了，而不是工具。要归因得做对照（有清单 / 无清单两组），而试点期样本量大概率不够。
- **不测机会成本**：把设计师的时间省下来之后用来做什么，这份模型不回答。
- **单价随时会变**：这份模型给的是 token 与公式，钱的部分用之前按官网核对。
