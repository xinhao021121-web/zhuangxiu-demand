## 一、目标与范围

### 1.1 要支撑的形态

| 形态 | 载体 | 定位 |
| --- | --- | --- |
| 微信小程序 | 房主手机 | 正式产品，长期维护 |
| Web | 房主电脑 | 正式产品，长期维护 |
| 展示版 | 浏览器 | 演示与作品展示，不承担产品职责 |

三者是同一个产品的三种呈现：字段、规则、文案、指标完全一致，差异只在布局与导航方式。产品文档 3.1 已经把两端的信息架构分别写清楚了。

### 1.2 V1 的技术范围

做：填写页（含空间实例增删）、纯规则发现引擎、发现卡片三动作闭环、双进度指标、断点恢复、需求摘要、静默模式、埋点。

不做：后端服务、模型调用、多角色与权限、设计师端、跨项目记忆。产品文档 6.2 已列出的产品边界同样适用。

### 1.3 前提

以下三条是选型的输入，任何一条发生变化都要重新评估本方案（见第九章）：

1. 微信小程序与 Web 服务的是同一批房主、同一张需求表，差异只在布局。
2. 小程序是最终上线形态，Web 是同一产品的桌面场景，两者都要长期维护。
3. 展示版不是产品，不参与长期迭代。

## 二、技术选型

### 2.1 选型结论

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | TypeScript | 领域模型的类型化本身是资产 |
| 跨端框架 | Taro + React | 一套代码产出 weapp 与 h5 两个产物 |
| 状态管理 | Zustand | 表单状态是一棵可序列化的树 |
| 样式 | CSS 变量 + 媒体查询 | 宽窄两套布局靠断点分支 |
| 组件库 | NutUI-React | 只用于基础控件，表单主体自研 |
| 领域层 | 纯 TypeScript 包 | 零框架依赖，三端共用 |
| 测试 | Vitest + Playwright + miniprogram-automator | 分三层，见第六章 |
| 包管理 | pnpm workspace | 领域包与应用的唯一共享方式 |
| 后端 | V1 不引入 | 草稿走本地存储，见 4.6 |

### 2.2 为什么是 Taro

**两端差异是布局差异，不是产品差异。** 宽屏是左右分栏，窄屏是手风琴加底部横条，这是响应式能解决的问题。如果为布局差异维护两份界面，成本不在于写第一遍，而在于之后每一次改动都要同步两遍，而且同步错了不容易发现。

**两端行为不会漂移。** 一套代码改一处两端都对。

**可自动验证的覆盖面最大。** H5 产物能在无头浏览器里跑完整流程；小程序端的验证链条是断的（没有开发者工具就没有稳定自动化）。同源之后，无头浏览器覆盖的就是两端共用的那部分逻辑，剩下没覆盖的只有平台适配层。

**选型可逆。** 领域逻辑抽成纯 TS 包后与框架解耦，换框架的代价被限制在渲染层。

### 2.3 明确不选

**不上 Formily 这类 schema 表单框架。** 191 个字段、可增删的空间实例、房型决定字段显隐、"其他补充"的写回与撤销，这套逻辑用重型方案表达出来的配置成本高于手写自研渲染器，而且不好调试。自研渲染器已经在两版 Demo 里跑通。

**不用 uni-app。** 能力与 Taro 等价，差别是 Vue 还是 React。选 React 是因为 AI 辅助开发时语料更厚，遇到问题更容易定位。

**不让展示版影响架构。** 展示版是 H5 产物的一个副产品，不为它单独设计代码结构。

### 2.4 唯一没有把握的地方

Taro 的主场是移动端 H5，用它承载宽屏 Web 是次要场景，需要额外处理两件事：

1. 关闭 Taro 的 rem 适配，改用 px 加媒体查询，否则宽屏下尺寸会被拉伸得不合理。
2. 宽屏 Web 的路由与样式隔离需要按桌面习惯单独配。

这件事在 M1 阶段就要验证（见第八章），验证不过就执行第九章的退路。

## 三、架构分层

### 3.1 三层结构

```
┌──────────────────────────────────────────────────────┐
│  呈现层（Taro 页面与组件）                            │
│  · 壳组件：表单容器、助手容器、分区导航（按端分支）    │
│  · 字段控件：chips / 输入 / 长文本 / 实例卡片（共享）  │
├──────────────────────────────────────────────────────┤
│  领域层（纯 TypeScript 包，零框架依赖）                │
│  · field-spec  字段规格与校验                         │
│  · rules       规则引擎与建议计算                     │
│  · summary     需求摘要与意向书文本                   │
│  · data        数据仓储接口                           │
├──────────────────────────────────────────────────────┤
│  适配层                                               │
│  · 本地存储（Taro.setStorage，两端自动映射）           │
│  · 埋点上报（V1 本地记录，后续接云端）                 │
└──────────────────────────────────────────────────────┘
```

**分层纪律**：领域层不 import 任何 Taro 或 React 的东西；呈现层不自己算业务结论，只做渲染和事件派发。这条纪律是整套方案能否成立的前提。

### 3.2 跨端分支的边界

允许分支的地方只有三个壳组件：

| 壳组件 | 宽屏（Web） | 窄屏（小程序 / 展示版） |
| --- | --- | --- |
| 表单容器 | 多列网格，大类可同时展开 | 单列，手风琴一次只开一个 |
| 助手容器 | 右侧常驻侧栏 | 底部常驻横条 + 半屏弹层 |
| 分区导航 | 竖直进度点 | 顶部横滑胶囊 |

**判定信号**：一旦平台判断开始出现在字段控件的渲染里，说明两端差异比预估的大，此时应当拆成两套界面、共用一个领域包，而不是继续加条件编译。

### 3.3 目标仓库结构

```
装修需求采集助手/
  app/                  # Taro 应用（weapp + h5）
  packages/
    field-spec/         # 字段规格 JSON、类型、校验
    rules/              # 规则引擎
    summary/            # 摘要生成
    data/               # 数据仓储接口与本地实现
  tools/                # 字段清单 Excel → JSON
  docs/                 # 产品文档与技术方案
  demo/  mobile/        # 现有 H5 Demo，作为交互设计稿保留
  tests/                # 端到端与冒烟测试
```

`demo/` 与 `mobile/` 保留但不再演进：它们记录了两端的信息架构取舍，是 `app/` 实现时的参照物。

## 四、关键设计

### 4.1 字段规格：单一来源

字段清单 Excel 是唯一的人类编辑入口，构建脚本把它导出为 `packages/field-spec` 的 JSON，前端渲染、规则引擎、摘要生成、导出全部引用同一份数据。

字段结构沿用现有形态：

```json
{
  "id": "kt_hood",
  "section": "厨房", "group": "油烟与灶具",
  "label": "油烟机形式", "type": "单选",
  "options": ["顶吸", "侧吸", "集成灶"],
  "suggest": "选填", "scope": "固定", "applies": "全部"
}
```

`scope` 区分固定分区与空间实例分区，`applies` 描述房型适用性。字段 ID 是前端数据键，一旦发布不做重命名。

### 4.2 字段渲染：元数据驱动

渲染器接收「字段定义 + 当前值 + 是否带助手标记」，输出对应控件。三类控件覆盖全部 191 个字段：选项组（单选 / 多选）、输入（文本 / 数字 / 日期）、长文本。

渲染决策（出哪种控件、可选项是什么、是否显示）是纯函数，放在 `field-spec` 里用 Vitest 测；真正的渲染实现很薄，两端共用同一套。

### 4.3 规则引擎

规则分两部分：

- **元信息**（可序列化）：`id`、优先级、发现类型、目标字段、写入动作、文案模板、依据模板。
- **谓词**（触发条件）：判断当前表单快照是否命中，并给出发现项。

谓词在 V1 中用 TypeScript 承载，因为它需要按空间实例展开（例如「任一卫生间选了浴缸 → 针对该实例生成一条发现」），纯声明式结构表达不了。计算接口保持纯函数形态：输入表单快照，输出发现项数组，中间不读全局状态、不产生副作用。

为了让规则能在不发版的前提下调整，接口层面预留云端覆盖：规则元信息与谓词标识从远端读取，命中判断仍在客户端执行。V1 先内置，接云端时不改调用方。

执行时需要保证的四件事：

1. 同一条发现在一次会话中只出现一次。
2. 风险提醒被「保持需求」后不再重复出现。
3. 发现项按 P0 → P1 → P2 排序，风险提醒优先。
4. 连续 3 次「不感兴趣」进入静默，静默状态只属于本次会话。

### 4.4 状态与草稿

状态是一棵可序列化的树，包含四部分：表单值（固定字段与各空间实例）、发现处理状态、静默与计数、结构版本号。

整棵树序列化后写入本地存储，读回时按 `schemaVersion` 做迁移。字段清单升级（增删字段、改选项）时必须保证旧草稿可读——这是唯一需要版本迁移机制的地方。

### 4.5 摘要与输出物

需求摘要由模板拼装已填字段与已确认的发现，不调用模型，长度控制在 150 字以内。摘要是纯函数，放在 `summary` 包里。

《需求意向书》与《量房确认清单》在 V1 中沿用产品文档的待确认项结论，先不实现导出。小程序内没有打印能力，后续要走生成图片或 PDF 分享，或者等设计师端承接。

### 4.6 数据层

V1 不引入后端。仓储接口放在 `data` 包里，V1 只提供本地实现（`Taro.setStorage`，两端自动映射到 `localStorage` 与 `wx.storage`）。

接口按将来要接的能力设计：读草稿、写草稿、提交需求、上报埋点。这样接入云端时只换实现，不动调用方。

接入后端时优先考虑微信云开发，因为它免服务器、免备案域名；但云开发只在小程序端可用，H5 端需要走云开发的 HTTP 接口或另建服务，届时由数据层遮蔽差异。

## 五、工程原则：把逻辑放在能自动验证的地方

这是本项目最重要的一条工程约束，其他细节都可以让步。

小程序端没有稳定的自动验证手段：AI 改完代码无法自己跑起来看结果，只能依赖人在开发者工具里确认。Web 端相反，无头浏览器可以完整跑通流程并截图。所以架构上要主动把逻辑从渲染层挤进领域层：

- 规则命中、优先级排序、去重、静默状态机、摘要生成、字段校验、草稿迁移，全部是纯函数，在 Node 里用 Vitest 跑。
- 呈现层只做「读状态、渲染、派发事件」，越薄越好。

目标是把无法自动验证的代码占比压到最低。

## 六、质量保障

### 6.1 三层测试

| 层 | 工具 | 覆盖 | 谁能跑 |
| --- | --- | --- | --- |
| 领域包 | Vitest | 规则命中、排序去重、静默状态机、摘要、字段校验、草稿迁移 | AI 可独立跑 |
| H5 产物 | Playwright | 端到端流程、两端布局指标、截图 | AI 可独立跑 |
| 小程序端 | miniprogram-automator | 平台适配层、真机手势 | 需要开发者工具，可能人工 |

### 6.2 已有资产

`tests/demo.smoke.mjs`（34 项）与 `tests/mobile.smoke.mjs`（63 项）已经在跑，覆盖了添实例、选房型、填示例、定位、采纳、改一改、撤销、静默、摘要、提交前检查、重置，以及移动端布局指标（无横向溢出、横条与操作栏不重叠、触控高度、按需渲染字段数）。迁移到 Taro 时这套断言直接复用，测试脚本的写法不用变。

### 6.3 必须守住的验证点

- 规则引用的目标字段必须存在于字段清单（防止字段清单与规则漂移）。
- 字段清单注入的字段数量与 Excel 一致。
- 直接打开构建模板文件不能出现空白页或 NaN。
- 控制台无错误。

### 6.4 本机环境注意

Playwright 自带的 Chromium 在部分机器上因缺少运行库无法启动（报并行配置错误）。测试脚本已支持逐个尝试内核并回落到系统 Chrome 或 Edge，也可以用 `PLAYWRIGHT_CHROMIUM` 环境变量手动指定。

## 七、构建与发布

**字段数据**：改字段清单 Excel 后运行 `python tools/build_mobile_demo.py` 一类的构建脚本导出 JSON，禁止手工编辑导出结果。

**小程序端**：微信开发者工具上传，V1 需要准备的合规项包括类目（工具）、隐私协议声明、用户填写内容的收集说明。个人主体不能获取手机号，产品设计上不要依赖它。

**H5 / 展示版**：构建产物部署为静态站点，同一份产物在宽屏下即 Web 端，窄屏下即展示版。H5 端不使用任何小程序专属 API。

## 九、风险与退路

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| Taro 扛不住宽屏 Web | M1 中宽屏布局需要大量平台判断才能实现 | 拆成两套界面 + 共用一个领域包 |
| 布局分支渗透进字段层 | 单个字段控件里出现平台判断 | 同上，不要继续加条件编译 |
| 小程序端长表单性能不足 | 真机上展开大类时卡顿 | 加深分包与懒渲染；必要时按大类拆页面 |
| 个人主体类目受限 | 提审被要求补充资质 | 收紧名称与简介表述，向「工具」靠；必要时调整上线计划 |
| 依赖框架导致返工 | 领域包里出现框架 import | 立即停下修边界，这是分层的底线 |

退路始终有效，因为领域包与框架无关。这是把领域层抽出来的主要目的。
