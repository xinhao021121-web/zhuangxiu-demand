## 一、为什么做

### 1.1 问题

现有版本的助手能回答「你还漏了什么」，但回答不了「你刚才那句话是什么意思」。

房主的真实表达是「我买了个 89 平的，一家三口，喜欢简单一点的」，而表单要的是 13 个大类、191 个结构化字段。这条翻译鸿沟留下两个缺口：

| 缺口 | 表现 | 现有规则引擎为什么补不上 |
| --- | --- | --- |
| 模糊表达落不了地 | 「简单一点」「住得舒服」映射不到任何字段 | 规则判的是「已填的值之间是否矛盾」，理解不了没被结构化的自然语言 |
| 表达门槛高 | 房主要先知道「无主灯」「干湿分离」这类词才填得动 | 规则不会追问，也不会把用户的话翻译成术语 |

### 1.2 与发现引擎的分工

这是本模块最重要的一条边界：两个能力解决的是两类问题，不是同一个问题的两种实现。

| | 发现引擎（已实现） | 需求理解 Agent（本模块） |
| --- | --- | --- |
| 解决的问题 | 已填内容之间还缺什么、哪里有矛盾 | 用户表达的意思是什么、怎么落到字段 |
| 输入 | 结构化的表单快照 | 自然语言 |
| 判断性质 | 确定映射，可枚举、可单测 | 语义理解，本质是概率问题 |
| 为什么不用同一种技术 | 确定映射不该交给模型，那会把可复现的结论变成不可复现的 | 语义理解交给规则会退化成关键词匹配，覆盖不了同义表达 |

两者的关系是**联合而非替代**：对话回填后仍由规则引擎做二次发现（新填的字段可能触发新的发现项），规则引擎同时充当兜底——模型不可用时，产品回落为现有版本的行为。

### 1.3 产品定义

在现有需求填写页上加一条对话通道。房主直接说，Agent 把听懂的部分变成一张「理解确认卡」交给房主核对，确认后由本地代码写回表单。

**模型只产出候选值，永远不直接写表单。**

## 二、目标用户与场景

### 2.1 优先服务谁

沿用产品文档的三类画像，本模块最该服务的是**小白型**：他们不是不想说，是不知道要说成什么样。

### 2.2 核心场景

**场景一：一句话开局。** 房主进入填写页，Agent 问「房子多大、几口人住」，房主答「89 平，一家三口，有个刚上小学的孩子」。Agent 识别出面积、常住人口、孩子年龄三段信息，生成 3 条理解项请房主确认。

**场景二：模糊表达被追问。** 房主说「想要简单一点的」。这个词对应不到任何字段，Agent 不猜，而是追问「您说的简单，更接近哪种？」，给出选项，并说明为什么问（影响主材选型与预算分配）。

**场景三：两条路径互相认得。** 房主先在表单填了预算，切到对话说「风格想要原木」。Agent 不再重复问预算，只在理解卡里列风格；确认后表单的风格字段立即更新。

**场景四：模型不可用。** 没有网络或没有配置 Key 时，对话入口明确提示不可用，产品静默回落到现有版本——表单与规则发现照常可用，不出现半死状态。

## 三、核心流程

### 3.1 双路径并行

表单路径与对话路径实时互认：表单已填的字段进入对话上下文（Agent 不重复追问），对话确认的回填写回表单。同一字段两侧都被修改时，以最后一次操作为准，并记录操作来源。

### 3.2 对话路径主流程

```
进入填写页
  → Agent 开场 + 摸底问题（每轮不超过 2 问）
  → 房主自然语言表达
  → 意图识别 + 字段映射 + 置信度评估
  → 生成理解确认卡（字段 → 理解值 → 置信度 → 依据原话）
  → 房主逐条确认 / 修改 / 拒绝
  → 本地代码写回表单（带「助手建议 · 撤销」标记）
  → 规则引擎基于新表单重新计算
  → 需求清晰度更新 → 触发下一轮（缺失或歧义）
  → 提交前生成需求摘要
```

### 3.3 关键约束

- 模型不写表单：写入由用户确认后触发确定性代码执行，沿用现有 F2 的三动作链路。
- 字段已有值时只建议不覆盖，替换要二次确认（现有行为不变）。
- 每条理解都能点开看到依据原话；给不出依据的，只能变成追问，不能变成回填。
- 追问每轮不超过 2 个问题；连续跳过触发打扰控制，沿用现有静默模式。

## 四、主要功能

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| A1 | 对话入口与摸底提问 | P0 | 桌面端停在助手侧栏内，手机端进发现弹层；开场主动问不超过 2 个高价值问题 |
| A2 | 自然语言理解与字段映射 | P0 | 把用户的话映射到字段清单白名单内的字段，附带置信度 |
| A3 | 理解确认卡 | P0 | 字段名 + 理解值 + 置信度 + 依据原话 + 确认 / 修改 / 拒绝，是本模块的核心界面 |
| A4 | 结构化回填 | P0 | 确认后由本地代码写入表单并标记可撤销；落不到字段的内容进所属大类的「其他补充」 |
| A5 | 歧义追问 | P1 | 置信度低或多义表达不猜，改成带选项的追问，并说明追问理由 |
| A6 | 反馈闭环与打扰控制 | P1 | 采纳 / 修改 / 拒绝 / 跳过全部留痕；连续拒绝进入静默 |

### A2 的边界：只理解房主答得上的字段

识别范围与产品文档 3.4 的采集边界一致。层高、承重墙、上下水点位这类专业信息，即使房主主动提到，也只作为备注记录，不进表单字段——那 16 项属于《量房确认清单》，由设计师现场确认。

## 五、AI 能力设计

### 5.1 输入

三类：对话文本、当前表单快照（用于判断哪些字段已填、避免重复追问）、字段清单白名单（合法的目标字段）。

### 5.2 输出契约

沿用一套统一输出结构，本模块主要用其中四类：

| 类型 | 用途 |
| --- | --- |
| understanding | 理解确认卡（核心输出） |
| question | 歧义追问卡 |
| suggestion | 与理解相伴的建议，如「儿童成长空间建议预留弹性收纳」 |
| summary | 提交前的需求摘要 |

每条输出的公共字段：类型、内容、置信度、依据（原话或知识条目）、免责等级、反馈入口。

### 5.3 可靠性设计

| 风险 | 处置 |
| --- | --- |
| 编造房主没说过的信息 | 硬规则：字段值必须能在用户原话里找到依据，找不到就只能降级为追问，不能回填 |
| 置信度虚高 | 置信度由可判定的信号决定（原话是否明确、是否多义、是否与已填内容冲突），不由模型自评 |
| 输出格式跑偏 | 单条解析失败只丢那一条，其余照常渲染；整份解析失败重试一次 |
| 模型整体不可用 | 回落现有版本（表单 + 规则发现），对话入口明确提示不可用 |

## 六、指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 对话路径完成率 | 经对话完成提交的会话占比 | ≥ 30% |
| 理解项采纳率 | 采纳数 / 理解项展示数 | ≥ 30% |
| 理解修正率 | 用户修改后采纳 / 全部采纳 | 越低越好，作为理解质量的辅助线 |
| 编造率 | 回填值无法溯源到用户原话的条数 | 0 |
| 追问打扰度 | 每轮平均追问数、跳过率 | ≤ 2 问 / 轮，跳过率 < 40% |

验证方式沿用「编造即失败」的思路：准备一组固定对话样本，每条样本标注「应当识别出哪些字段」，跑回归同时看识别情况与编造情况。样本规模见待确认项 2。

## 七、版本与边界

| 版本 | 范围 |
| --- | --- |
| V0.1（本模块 MVP） | 对话理解 + 理解确认卡 + 结构化回填 + 与规则引擎联合计算；先覆盖 6 类高频信息（面积、常住人口、风格、预算、宠物、设备与智能） |
| V0.2 | 扩展到全字段、歧义追问、把反馈用于优化提示词 |
| 后续 | 需求摘要升级为可溯源的结构化交付物，接下游设计师端 |

明确不做：

- 不做闲聊，不做装修工艺与材料知识解答；
- 不替房主做设计判断，不给报价与工期承诺；
- 不修改用户已填内容，不静默写表单；
- 不做多模态输入（图片、语音）。

## 八、待确认项

| # | 内容 | 影响 |
| --- | --- | --- |
| 1 | 模型接入方式：用户自带 Key，还是走一个轻代理（自带 Key 与「数据不出本机」的现状冲突，代理需要部署与成本） | 决定数据流向与隐私表述，优先级最高 |
| 2 | 首版是否就取 6 类高频字段，评测样本集做多大 | 决定工程量与评测工作量 |
| 3 | 置信度三级（高 / 中 / 低）的判定阈值怎么定 | 影响追问频率与打扰度 |
| 4 | 对话记录是否进草稿持久化，还是只保留本次会话 | 影响断点恢复体验与本地存储体积 |
| 5 | 用户修改类反馈是否回流用于优化提示词，以什么形式留存 | 决定「越用越准」是否可验证 |
