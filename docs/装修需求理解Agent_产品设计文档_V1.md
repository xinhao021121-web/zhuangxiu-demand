## 一、为什么做

### 1.1 现有版本留下的缺口

V1.0 把两件事做完了：13 个大类、191 个字段的填写页，以及用确定性规则做的发现引擎。但输入只有表单一种，房主必须先把想法翻译成选项，才填得进去。

房主的真实表达是「我买了个 89 平的，一家三口，喜欢简单一点的」，而表单要的是选项。这条鸿沟留下两个缺口：

| 缺口 | 表现 | 现有规则引擎为什么补不上 |
| --- | --- | --- |
| 模糊表达落不了地 | 「简单一点」对应不到「装修风格偏好」里的任何一个选项 | 规则判的是「已填的值之间是否矛盾」，处理不了没被结构化的自然语言 |
| 表达门槛高 | 房主要先知道「无主灯」「干湿分离」这类词才填得动 | 规则不会追问，也不会把用户的话翻译成选项 |

### 1.2 与发现引擎的分工

这是本篇最重要的一条边界：两个能力解决的是两类问题，不是同一个问题的两种实现。

| | 发现引擎（V1.0 已实现） | 需求理解 Agent（本模块） |
| --- | --- | --- |
| 解决的问题 | 已填内容之间还缺什么、哪里有矛盾 | 用户这句话是什么意思、对应哪些字段 |
| 输入 | 结构化的表单快照 | 自然语言 |
| 判断性质 | 确定映射，可枚举、可单测 | 语义理解，本质是概率问题 |
| 为什么不用同一种技术 | 确定映射不该交给模型，那会把可复现的结论变成不可复现的 | 语义理解交给规则会退化成关键词匹配，覆盖不了同义表达 |

两者的关系是**联合而非替代**：对话回填后仍由规则引擎做二次发现（新填的字段可能触发新的发现项），规则引擎同时充当兜底——模型不可用时，产品回落为 V1.0 的行为。边界一句话：**模型只做理解与追问，不产出发现、建议与摘要**——这三样仍由规则引擎与模板负责（见 5.2）。

### 1.3 本模块做什么

在现有填写页上加一条对话通道。房主直接说，Agent 把听懂的部分变成一组「理解条目」交给房主核对，确认后由本地代码写回表单。

**模型只产出候选值，永远不直接写表单。**

输入通路从一条变成两条，但产品只有一个：同一个草稿、同一套字段规格、同一套规则、同一个需求清晰度（见第六章）。

## 二、目标用户与场景

### 2.1 优先服务谁

沿用产品文档 2.1 的三类画像，本模块最该服务的是**小白型**：他们不是不想说，是不知道要说成什么样。

### 2.2 核心场景

**场景一：一句话开局。** 房主进入填写页，Agent 问「房子多大、几口人住」，房主答「89 平，一家三口，有个刚上小学的孩子」。Agent 识别出三段信息，分别对应字段规格里的「建筑面积」「常住人口构成」「成员年龄」，生成 3 条理解条目请房主确认。

**场景二：模糊表达被追问。** 房主说「想要简单一点的」。这句话对应不到「装修风格偏好」的任何选项，Agent 不猜，而是追问「您说的简单，更接近哪种？」，给出该字段已有的选项，并说明为什么问。

**场景三：两条通路互相认得。** 房主先在表单填了预算，切到对话说「风格想要原木」。Agent 不再重复问预算，只在理解列表里列风格；确认后表单的风格字段立即更新，需求清晰度同步上涨。

**场景四：模型不可用。** 没有网络或没有配置 Key 时，对话入口明确提示不可用，产品静默回落到 V1.0——表单与规则发现照常可用，不出现半死状态。

## 三、核心流程

### 3.1 两条输入通路实时互认

表单已填的字段进入对话上下文（Agent 不重复追问「常住人口构成」这类已填项），对话确认的回填写回表单。同一字段两侧都被修改时，以最后一次操作为准，并记录操作来源。

### 3.2 对话通路的主流程

```
进入填写页
  → Agent 开场 + 摸底提问（每轮不超过 2 问）
  → 房主自然语言表达
  → 识别：这句话对应哪些字段、值是什么
  → 生成理解条目（字段 → 值 → 依据原话）
  → 房主逐条确认 / 改一改 / 不感兴趣
  → 本地代码写回表单（带「助手建议 · 撤销」标记）
  → 规则引擎按现有防抖重算，给出发现项
  → 需求清晰度更新 → 触发下一轮（缺项或歧义）
  → 提交前生成需求摘要（沿用 F5 模板，不经过模型）
```

### 3.3 与规则引擎的先后关系

两条通路都会向用户提问，必须避免互相打扰：

| 情形 | 处置 |
| --- | --- |
| 同一字段既有发现项、又在对话里被追问 | 以发现项为准，追问跳过该字段——发现项的触发条件是确定的，成本更低 |
| 对话确认写入后 | 走现有防抖触发一次规则引擎重算，新发现项按现有优先级排序进入发现列表 |
| 用户正在对话中 | 发现列表不抢焦点、不自动跳转，文案与高亮沿用现有交互细则 |
| 连续忽略 | 理解条目的「不感兴趣」与发现项的「不感兴趣」共用连续计数，连续 3 次进入静默（F6） |
| 静默期间 | 发现项不再主动提示；对话追问由用户主动发起，不受静默影响 |

### 3.4 关键约束

- 模型不写表单：写入由用户确认后触发确定性代码执行，沿用现有 F2 的三动作链路。
- 字段已有值时只建议不覆盖，替换要二次确认（现有行为不变）。
- 每条理解都能点开看到依据原话；给不出依据的，只能变成追问，不能变成回填。
- 追问每轮不超过 2 个问题。

## 四、主要功能

功能编号接续产品文档的 F1–F8。

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| F9 | 对话入口与摸底提问 | P0 | 桌面端停在助手侧栏内，手机端进底部发现横条展开的弹层；开场主动问不超过 2 个高价值问题 |
| F10 | 自然语言理解 | P0 | 把用户的话映射到字段清单白名单内的字段与选项 |
| F11 | 理解条目与确认 | P0 | 字段名 + 值 + 依据原话 + 确认 / 改一改 / 不感兴趣，是本模块的核心界面 |
| F12 | 结构化回填 | P0 | 确认后由本地代码写入表单并标记可撤销；落不到字段的内容进所属大类的「其他补充」 |
| F13 | 歧义追问 | P1 | 对应不到明确值的表达不猜，改成带选项的追问，并说明追问理由 |
| F14 | 反馈与打扰控制 | P1 | 沿用 F2 / F6 的机制；额外记录理解条目被改一改的样本，作为识别偏差的回归素材 |

### F10 / F13 的边界：只理解房主答得上的字段

识别范围与产品文档 3.4 的采集边界一致。层高、承重墙、上下水点位这类专业信息，即使房主主动提到，也只作为备注记录，不进表单字段——那 16 项属于《量房确认清单》，由设计师现场确认。

## 五、AI 能力设计

### 5.1 输入

三类：对话文本、当前表单快照（用于判断哪些字段已填、避免重复追问）、字段规格白名单（合法的目标字段与选项）。

### 5.2 模型输出什么

模型每次返回一组条目，只有两种：

| 类型 | 用途 |
| --- | --- |
| 理解条目 | 字段 + 值 + 依据原话（回填候选） |
| 追问条目 | 字段 + 问题 + 选项 + 追问理由 |

刻意不产出发现、建议与摘要：基于已填内容推导的建议属于发现引擎的职责（产品文档 4.2），需求摘要由模板拼装、不调用模型（产品文档 4.6）。模型在这里只回答一个问题——用户这句话对应哪些字段。

### 5.3 什么条件下才能回填

每个候选值必须同时满足三条，才进入「待确认」列表；任一不满足，只能变成追问：

| 条件 | 判据 | 谁来判 |
| --- | --- | --- |
| 有原话依据 | 模型必须一并返回它依据的原话片段，本地校验该片段确实是用户原话的子串 | 本地代码 |
| 值合法 | 能对上字段规格里的选项或类型（field-spec 的校验） | 本地代码 |
| 不冲突 | 与当前表单快照不矛盾 | 规则引擎（复用现有冲突检测） |

三条都是可判定的，不依赖模型自报置信度。这也是本模块不做「置信度分级」的原因：需要模型自评的分数，既无法验证，也不影响这三条判据的结论。

### 5.4 可靠性设计

| 风险 | 处置 |
| --- | --- |
| 编造房主没说过的信息 | 硬规则：候选值必须能在用户原话里找到依据，找不到就只能降级为追问，不能回填 |
| 值落不到字段 | 只能对上选项或类型的值才可回填，落不到字段的内容进所属大类的「其他补充」 |
| 模型输出格式跑偏 | 单条解析失败只丢那一条，其余照常渲染；整份解析失败重试一次 |
| 模型整体不可用 | 回落 V1.0（表单 + 规则发现），对话入口明确提示不可用 |

## 六、与现有实现的接口

本模块不新建领域包，也不新起一套状态，全部长在现有结构上。

| 现有能力 | 落点 | 本模块怎么用 |
| --- | --- | --- |
| 字段规格 | packages/field-spec | 目标字段白名单、选项与类型校验、房型决定可见字段；回填后 sectionStats 直接反映到需求清晰度 |
| 规则引擎 | packages/rules | 回填后重算发现；发现项优先于追问；冲突检测复用现有实现 |
| 需求摘要 | packages/summary | 不变，仍是模板拼装 |
| 草稿与迁移 | packages/data | 沿用现有 Draft；对话记录是否入库见待确认项 2，若入库需按 schemaVersion 迁移 |
| 助手标记 | draft.aiMarks 与「助手建议 · 撤销」 | 沿用，不新增标记类型——规则写入与对话写入对用户是同一种东西 |
| 防抖与提交路径 | app/src/store.ts | 对话回填走同一条提交路径，不另开一条 |
| 静默与打扰控制 | packages/rules 的 state.ts | 理解条目的「不感兴趣」与发现项共用连续计数 |
| 领域包边界 | 技术方案 3.1 | 模型调用不进领域包；领域包保持纯函数、可在 Node 里单测 |

## 七、指标

本模块不新造一套指标体系，主指标挂在产品文档第七章已有的定义上；后两项是本模块新增的观测项。

| 指标 | 定义 | 目标 | 来源 |
| --- | --- | --- | --- |
| 提交时推荐项完成率 | 提交时已填推荐项 / 全部推荐项 | ≥ 80% | 产品文档七章（本模块应当抬升它） |
| 理解条目采纳率 | 采纳数 / 展示数 | ≥ 30% | 与发现采纳率同口径 |
| 编造率 | 回填值无法溯源到用户原话的条数 | 0 | 本模块新增 |
| 静默触发率 | 进入静默的会话占比 | < 5% | 产品文档七章（本模块不应推高它） |
| 使用对话的会话占比 | 至少用过一次对话的会话占比 | 先取基线，再定目标 | 本模块新增 |

验证方式：沿用产品文档第七章的三个种子场景（首次装修小白、养猫的三口之家、改善型换房），每个场景补一段自然语言输入，跑回归同时看识别情况与编造情况；样本集规模见待确认项 4。

## 八、版本与边界

| 版本 | 范围 |
| --- | --- |
| V2.0（本模块，对应产品文档 6.1） | 对话式补充录入：对话入口、自然语言理解、理解条目确认、结构化回填、歧义追问 |
| V2.1 | 覆盖扩展到全字段；追问从固定选项扩展到多轮；理解偏差样本回流用于优化提示词 |
| 不在本模块 | 产品文档 6.1 V2.0 里的「模型辅助场景挖掘」与「App 端」 |

关于「模型辅助场景挖掘」：场景挖掘已经是规则引擎的三类机制之一（产品文档 4.2），再列一项同名能力会造成两处实现。建议要么澄清它指什么，要么从 V2.0 范围里去掉——见待确认项 3。

明确不做（沿用产品文档 6.2）：

- 不做闲聊，不做装修工艺与材料知识解答；
- 不替房主做设计判断，不给报价与工期承诺；
- 不修改用户已填内容，不静默写表单；
- 不做多模态输入（图片、语音）。

## 九、待确认项

| # | 内容 | 影响 |
| --- | --- | --- |
| 1 | 模型接入方式：用户自带 Key，还是走一个轻代理（自带 Key 与「数据不出本机」的现状冲突，代理需要部署与成本） | 决定数据流向与隐私表述，优先级最高 |
| 2 | 对话记录是否进草稿持久化，还是只保留本次会话 | 影响断点恢复体验、本地存储体积与 schemaVersion 迁移 |
| 3 | 产品文档 6.1 的 V2.0 含「模型辅助场景挖掘」，与 4.2 的场景挖掘机制重叠，需要澄清指什么或从范围里去掉 | 避免两处实现同一个能力 |
| 4 | 首版覆盖哪些字段、评测样本集做多大。建议取「推荐填写 9 项 + 发现规则的触发字段」——前者决定需求清晰度，后者决定发现质量 | 决定工程量与评测工作量 |
| 5 | 用户「改一改」产生的样本是否回流用于优化提示词，以什么形式留存 | 决定「越用越准」是否可验证 |
