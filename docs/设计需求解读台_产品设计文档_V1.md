## 一、产品定位

### 1.1 一份填好的需求单，正确用法不是照着做方案

采集发生在量房之前。房主填表时手上没有房屋数据——层高、管道位置、承重墙、采光、排水条件，这些都要到现场才能确认。于是需求单天然带着两类不确定性：

| 不确定性 | 从哪来 | 后果 |
| --- | --- | --- |
| 需求能不能落地，要现场才知道 | 房主没有房屋数据，涉及现场条件的判断答不准 | 照单做方案，到现场才发现做不了，返工 |
| 需求单装不下房主的全部意图 | 191 个字段能装「已经想到的」，装不下「没说出口的」和「自己还没想清楚的」 | 方案做出来了，房主说「我不是这个意思」 |

所以需求单的正确用法不是「直接照着做方案」，而是**带着它去量房，把不确定的问清楚**。

### 1.2 设计师真正需要的是一份问题清单

一份需求单交到设计师手上时，有价值的信息不只是「房主写了什么」，而是：

- 还有哪些没定？
- 哪些可能冲突？
- 哪些必须到现场才能确认？

这三个问题的答案，就是本产品的核心产出：**《量房沟通清单》**。

### 1.3 这个产品做什么

设计师导入房主的需求单，平台给出两个视图和一份输出：

```
需求单 JSON
   → 视图一：房主填写的原始表格
   → 视图二：Agent 生成的表格理解（画像 / 诉求 / 矛盾 / 待确认）
   → 输出：量房沟通清单（带去现场照着问）
```

表格理解是清单的依据，清单是表格理解的落地形态——两者不是两件事，是同一份解读的两种呈现。

### 1.4 替代方案与差异

| 替代做法 | 为什么不够 |
| --- | --- |
| 设计师自己通读表格 | 191 个字段要逐个看，容易漏；而且读到的只是「房主写了什么」，还要自己想「该问什么」 |
| 把表格粘给通用 AI 工具 | 模型拿到的是没有字段结构的文本，无法逐条溯源到字段，也不能保证不编造；房主的家庭与住址信息还直接外发了 |
| 用通用项目管理工具存需求单 | 解决的是「放在哪」，不是「看懂」 |

本产品的位置：**在已有的字段结构上做解读**——每条结论都能点回具体字段，输出的是带去现场的问题，而不是方案。

## 二、目标用户与场景

### 2.1 主用户

**设计师**，以及他的量房环节。三类画像里的「小白型」房主在上一个产品里已经被服务过；到这一步，需求单的完整度决定设计师能拿到多少信息。

### 2.2 典型场景

**出门前。** 设计师收到客户的需求单，导入后花几分钟过一遍清单，知道这次出门要问清楚哪几件事。

**现场。** 按空间逐条问，问的是房主自己没想到的角度——「您说的简单，是原木那种，还是更冷的现代感」，而不是照着表格念一遍。

**回来。** 清单上问过的问题与当场得到的答案，直接成为定方案方向的依据。

**成功的样子**：设计师不必临场回忆「这家人当时填了什么」，也不必赌房主那句模糊表达到底是什么意思。

## 三、输入：需求单 JSON

MVP 的输入是采集端导出的一个 JSON 文件，需要包含三部分：

| 部分 | 内容 | 来源 |
| --- | --- | --- |
| 表单数据 | 固定字段值与各空间实例的值，以字段 ID 为键 | 采集端的 form model |
| 助手来源标记 | 哪些字段是助手建议写入的 | 采集端的 aiMarks |
| 元信息 | 提交时间、字段清单版本（schemaVersion） | 采集端新增 |

采集端目前只导出一段摘要文本（`submit()` 的入参是 `{ summary: string }`），所以**给它加一个结构化导出，是这版 MVP 的前置任务**——不做这一步，台子拿不到可以理解的数据。

## 四、核心产出：量房沟通清单

### 4.1 每条清单项的结构

| 字段 | 说明 | 例 |
| --- | --- | --- |
| 问题 | 要当面问什么 | 厨房是否接受开放式 |
| 为什么问 | 依据 | 房主填了「下厨频率：经常」且「厨房形式：开放式」 |
| 现场要核实 | 需要现场条件才能判断的部分 | 烟道位置、排烟条件、燃气备案要求 |
| 关联字段 | 点回原始表格 | 厨房 · 下厨频率、厨房形式 |
| 分类 | 便于现场按空间走 | 厨房 |

### 4.2 清单项从哪来

四个来源产生的是候选，最终谁进清单由 4.3 的判据决定；其中前三个由数据推导，第四个是现成资产：

| 来源 | 说明 | 谁生成 |
| --- | --- | --- |
| 空缺的推荐项 | 推荐填写 9 项里没填的 | 规则（确定） |
| 房主答「不清楚」的项 | 采集端在涉及专业判断的字段上专门给了「不清楚 / 听设计师建议」选项，这些话等于房主明说「我不确定，你来定」，是量房时最该聊的 | 规则（确定） |
| 从已填内容推导的问题 | 由需求组合推出的、需要当面确认的点 | 模型生成 |
| 通用量房确认清单 | 采集端已有的 16 项现场核实内容 | 现成资产 |

第三条是模型唯一负责的部分。也因此，模型在这里的回答只有一种形态：**一条能被追问、能被设计师判断的问题**，而不是一个结论。

### 4.3 什么该进清单：按判据筛，不按条数筛

清单只放关键信息，但「关键」必须有可判定的标准，否则会退化成「把表格念一遍」。一条信息进入清单，当且仅当它满足下面任意一条：

| 判据 | 含义 | 例 |
| --- | --- | --- |
| 影响可行性 | 现场条件可能让这个需求落不了地 | 开放式厨房 + 高频下厨 → 烟道位置与排烟条件 |
| 影响方向 | 答案不同，方案方向就不同 | 房主写「想要简单一点」→ 原木、奶油还是现代简约 |
| 影响成本或工期 | 与预算、入住时间冲突 | 预算 20 万 + 全屋定制 + 计划三个月入住 |

反过来，不满足任何一条的不进清单。典型的「不该进」有三类：

- 房主已经答清楚、且与现场条件无关的（写了「电视」就不必再问要不要电视）；
- 字段空着但答案对方案没有影响的（某个「其他补充」没填）；
- 只是罗列信息，不构成一个要当面确认的问题的。

**只要是关键信息就都列出，不设条数上限。** 用条数卡清单，砍掉的往往是真正重要的问题，这条线不划算。

判据由模型初判，最终由设计师在清单上删减——「这条值不值得带到现场」，设计师比模型准。**删减的动作会被逐条记录下来**，用来回头调判据。

### 4.4 长度靠组织解决，不靠删减

清单可能变长，而现场时间有限，所以组织方式本身是设计的一部分：

- **按空间分组**：沿用 13 个大类，现场按空间走一遍，不用来回翻；
- **分两档排序**：必问（不确认就无法推进）在前，建议问在后——这是排序，不是删减；
- **顶部给计数**：「必问 6 条 · 共 14 条」，让设计师先知道要花多久；
- **折叠与勾选**：同一空间下的条目可折叠。

如果实际用下来清单长得用不完，那是筛得不够准，回去改判据——而不是在这里设一个数字。

### 4.5 硬约束

- 每条清单项必须能指到字段（或明确标为来自通用量房清单），指不到的不出现；
- 不编造房主没说过的需求；
- 清单项是问题，不是结论：写「厨房是否接受开放式」，不写「建议做开放式厨房」。

## 五、主要功能

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| F1 | 需求单导入与列表 | P0 | 导入采集端导出的 JSON；本地保存多份需求单，列表显示核心摘要、提交时间、完成度 |
| F2 | 原始表格视图 | P0 | 按 13 个大类还原房主填的内容，可折叠；标出推荐项完成情况；每条字段标出「房主填写 / 助手建议」 |
| F3 | 外发内容逐条确认 | P0 | 生成清单前逐条确认要外发的字段（见 7.4）；自由文本默认不外发 |
| F4 | 表格理解 | P0 | 客户画像、核心诉求、矛盾与风险、待确认项四块；清单从中提炼 |
| F5 | 量房沟通清单 | P0 | 按 4.1 的结构生成，按空间分组、按必问 / 建议问排序；点条目跳回对应字段；支持删减并可撤销 |
| F6 | 清单导出 | P0 | 导出 Markdown 或可复制文本，用于打印或带进现场 |
| F7 | 现场使用与记录 | P1 | 手机上逐条勾选「已问」、记一句话结论；这些记录是「清单有没有用」的唯一证据 |

F7 不放进 MVP，是因为 MVP 要先验证「清单对不对」；但它决定了两件事——清单能否闭环，以及优化清单的唯一数据从哪来。建议紧接着做。

## 六、AI 用在哪里

边界与采集端保持一致：确定的事交给代码，读懂人话的事交给模型。

| 内容 | 谁做 | 为什么 |
| --- | --- | --- |
| 完成度、空缺项、答「不清楚」的项 | 规则 | 都是字段级的确定判断，可枚举、可单测 |
| 字段之间的矛盾（预算与面积、工期与定制周期） | 规则 | 采集端的规则引擎已有这类规则，直接复用 |
| 从已填内容推导「要问什么、为什么问」 | 模型 | 需要理解需求组合的语义——「高频下厨 + 开放式厨房」意味着什么 |
| 把散落的 191 个字段归并成 3–5 条诉求 | 模型 | 属于归纳，规则做不了 |

模型的硬约束：每条输出必须附上它依据的字段 ID；指不到字段的，只能标为「来自通用量房清单」，不能写成结论。这样「编造即失败」就从一句原则变成一条可以写进单测的规则。

## 七、脱敏与数据边界

需求单里有房主的家庭信息与住址信息。生成清单要调用模型，意味着这些内容会离开本机，所以外发内容必须在本地先处理完再出去。

### 7.1 顺序：先做数据最小化，再谈脱敏

能不外发的就不外发。第四章列的四类来源里，前三类中有一大半是确定性判断——完成度、空缺项、答「不清楚」的项、字段之间的矛盾——这些由本地规则算出来，根本不经过模型。模型只收到「需要语义理解的那部分字段」，这本身是最有效的脱敏。

### 7.2 字段级三级策略

| 策略 | 字段 | 处理 |
| --- | --- | --- |
| 不外发 | 小区 / 楼盘名称 | 整条留在本地，不进入任何请求 |
| 泛化后外发 | 所在城市 → 城市等级；成员年龄、孩子性别与年龄 → 年龄段；计划动工 / 完工 / 入住时间 → 相对时间段 | 本地转换成粗粒度描述再外发 |
| 原样外发 | 选项类字段（预算区间、风格、宠物、居住成员构成、设备与系统等） | 本身就是粗粒度选项，不含可识别信息 |

### 7.3 自由文本单独处理

191 个字段里有 22 个是自由填写，其中 16 个是各分区的「其他补充 / 其他需求」。房主最可能在这里顺手写下姓名、电话、门牌号、工作单位。处理分两层：

1. **本地先识别与替换**：手机号、固定电话、身份证号、邮箱、门牌地址（路 / 街 / 号 / 栋 / 单元 / 室）、微信号；
2. **替换后再外发**，命中处换成占位符（如「[已隐去]」），原文只留在本地的需求单里。

中文人名不做自动识别——没有可靠的正则，硬做会误伤（把「想装新中式」这类词也当成人名）。这个缺口由 7.4 的逐条确认界面兜住：判决权交给看得见上下文的人。

### 7.4 外发前逐条确认

生成清单前先过一道确认界面，这是本模块的 P0 功能（F3）。

| 项 | 设计 |
| --- | --- |
| 确认对象 | 脱敏之后、真正要外发的内容；命中脱敏的位置标注「此处已隐去：手机号」，让设计师知道发生了什么 |
| 默认状态 | 选项类字段默认勾选；**自由文本默认不勾选**——它是唯一可能夹带人名的类别，而人名无法自动识别，所以这个类别要设计师主动判断 |
| 操作 | 逐条取消 / 重新勾选；顶部提示「未勾选的 N 条不会参与解读」，让代价可见 |
| 查看原文 | 需要判断时可在本地展开原文，原文不会随之外发 |
| 事后可查 | 每次生成在外发记录里留下字段清单与时间，存在本地需求单中 |

默认不外发自由文本会让解读少一部分输入，这是刻意的取舍：**多花十几秒确认，换不会误发房主姓名。**

### 7.5 一个反直觉的结论

脱敏会让模型看到的信息变少，但这对本产品不是损失：被拿掉的恰好是「住哪、几口人、具体想干什么」这类只有当面聊才说得清的内容——它们本来就该进量房沟通清单，而不是让模型去猜。

## 八、指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 清单可用率 | 生成后未被设计师删减的条目占比 | ≥ 70%（MVP 期即可测，不必等现场记录） |
| 遗漏率 | 量房后发现「该问而清单没列」的关键问题数 | 目标 0，先取基线（需要 F7 的记录） |
| 清单条数 | 单份清单的条目数 | 不设上限，作为筛得准不准的观测项 |
| 编造率 | 无法溯源到字段或通用清单的条目数 | 0 |
| 单份解读耗时 | 从导入到导出清单 | ≤ 5 分钟（设计目标，待实测） |

验证方式：用采集端的三个种子场景（首次装修小白、养猫的三口之家、改善型换房）各导出一份需求单，跑完整的导入 → 理解 → 清单 → 导出，人工判定清单可用率。

## 九、版本与边界

| 版本 | 范围 |
| --- | --- |
| 本版 MVP | 需求单导入与列表、原始表格视图、表格理解、量房沟通清单、清单导出 |
| 下一版 | 现场使用与记录、设计师自行补充清单条目、按删减与现场反馈调优判据、需求单与清单的分享链接 |
| 不在范围 | 方案设计、效果图、报价、房主与设计师的聊天、量房数据回填设计、账号与权限 |

明确不做：不做方案生成与报价承诺、不做房主端与设计师端的即时沟通、不做云端与账号体系（MVP 是本地应用）、不替设计师做设计判断——本产品只负责把该问的问题摆到台面上。
