## 一、目标与范围

### 1.1 要支撑的形态

| 形态 | 载体 | 阶段 | 定位 |
| --- | --- | --- | --- |
| 问需 · 采集 | 微信小程序、H5（Taro 一套代码两个产物） | 已有 | 正式产品，长期维护；H5 宽屏即 Web 端，窄屏即手机版（带 manifest 与 service worker，可添加到主屏幕），同一份窄屏产物也是展示版 |
| 问需 · 解读 | 桌面工作台（Next.js） | 已有 | 公司内部工具：导入 → 确认外发 → 表格理解 → 清单 → 导出 |
| 问需 · 现场 | 独立 PWA（Vite + React） | 已有 | 公司内部工具：按空间走、逐条勾选、记一句话结论 |
| API 服务 | Node + Hono | 已有 | 四个客户端的公共依赖：鉴权、需求单与清单、脱敏与模型、外发审计、现场记录 |

四者服务的是同一条链路：字段、规则、文案、判据完全一致，差异只在布局与动线。

### 1.2 V1 的技术范围

**做**：账号与角色、需求单导入与列表、原始表格视图、外发前逐条确认与脱敏、表格理解、清单生成与导出、外发审计、现场记录与离线同步、模型 adapter、契约层。

**不做**：解读端与现场端的方案生成与报价、分享链接、房主端与设计师端的即时沟通、多租户与对外注册、跨项目记忆。产品文档 11.2 列出的产品边界同样适用于本方案。

### 1.3 前提

以下五条是选型的输入，任何一条发生变化都要重新评估本方案（见第十一章）：

1. 采集端要上云，后端就不能挂在任何一个客户端上——它是四个客户端的公共依赖。
2. 服务、数据与模型全部在境内，不允许出现「房主数据 → 境外服务」的路径。
3. 采集端最终会改为提交到云端；文件导入只是同一个接口的另一种输入方式，不是长期形态。
4. **解读端与现场端只服务自己公司**，不对外销售。因此是单组织的内部系统：不做多租户、不做计费、不做对外注册。
5. 模型固定为 DeepSeek；换模型时只替换 adapter，上层不动。

## 二、技术选型

### 2.1 选型结论

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | TypeScript | 领域模型的类型化本身是资产；服务端与四个客户端共用 |
| 采集端 | Taro + React | 一套代码产出 weapp 与 h5 两个产物；h5 额外带手机版装机资产（manifest 与 service worker，见 9.1） |
| 桌面工作台 | Next.js（App Router）+ React | 分享页要服务端渲染，路由、鉴权、构建一体化 |
| 现场端 | Vite + React + PWA（service worker + IndexedDB） | 离线优先是它的主场；与桌面端共用领域包与契约，不共用构建 |
| API 服务 | Node + Hono（备选 Fastify） | 类型契约好、Docker 部署简单；团队变大再考虑 NestJS |
| 数据库 | 境内托管 Postgres + Drizzle（本地与测试用 `node:sqlite`） | 单组织，不做租户隔离；访问权限按角色控制 |
| 契约 | zod schema → 生成 OpenAPI，独立 `packages/contracts` | 四个客户端共用一个契约源，变更由类型检查兜住 |
| 鉴权 | API 侧自签 token | 公司内部账号：手机号验证码或企业微信扫码 |
| 样式 | CSS 变量 + 媒体查询（采集端）/ Tailwind + CSS 变量（两个设计师端） | 宽窄两套布局靠断点分支 |
| 状态 | Zustand（采集端表单树）；桌面端与现场端各用各的 | 表单状态是一棵可序列化的树 |
| 领域层 | `packages/*` 纯 TS 包 | 零框架依赖，服务端与四个客户端共用 |
| 模型 | DeepSeek（官方 API），型号 `deepseek-chat` | 接口在领域层定义，实现在服务端；换模型只换 adapter |
| 对象存储 | 境内 OSS / COS | 导出件与将来的分享图 |
| 测试 | Vitest + Playwright（+ miniprogram-automator） | 领域包 / API / 各端界面三层 |
| 包管理 | pnpm workspace | 领域包与应用的唯一共享方式 |
| 部署 | Docker + 公司自己的服务器或境内云主机 | 不引入 K8s |

### 2.2 为什么后端必须独立于任何一个客户端

**采集端也要上云，后端就不能挂在任何一个客户端上。** 一旦小程序变成把需求单提交到云端，后端就成了四个客户端的公共依赖，藏在某个 Web 框架的 route handler 里会很难看。独立之后，谁接入都是调用同一组接口。

**模型调用和脱敏必须在服务端。** 密钥不能进浏览器，脱敏要发生在任何外发之前，这两件事已经决定了服务端是一等公民，而不是可以后补的东西。

**领域逻辑是纯 TS，四个客户端与服务端共用。** 字段规格、规则命中、清单判据、脱敏替换全部是确定性的纯函数，放在包里之后，小程序、Web、桌面端、现场端与服务端跑的是同一份判断依据——这是「各端行为不漂移」的唯一可靠做法。

### 2.3 为什么前端是三个工程

**采集端一套代码两个产物，是因为两端差异是布局差异。** 宽屏是左右分栏，窄屏是手风琴加底部横条，这是响应式能解决的问题。为布局差异维护两份界面，成本不在于写第一遍，而在于之后每一次改动都要同步两遍，而且同步错了不容易发现。

**解读端要服务端渲染。** 产品后续要做的分享链接需要「一个不带登录态的只读页面」，这是服务端渲染的主场；鉴权中间件与构建一体化部署也省事。

**现场端拆出去，是因为它的难点和桌面端不一样。** 桌面端要的是服务端渲染与一体化部署，现场端要的是离线优先（service worker + 本地库 + 重连同步）和单手可操作的轻界面。塞进一个工程，只会让构建、缓存与离线策略互相迁就。

**拆开不等于各写一套逻辑。** 三个工程共享 `packages/*`（判据、合并、排序、脱敏）与 `packages/contracts`（接口契约），呈现层各写各的。UI 组件不抽公共包：三端组件差异大、复用率低，硬抽反而增加成本；真正该共用的是设计 token（同一套配色与字号）。

### 2.4 明确不选

- **不上 Formily 这类 schema 表单框架。** 191 个字段、可增删的空间实例、房型决定字段显隐、「其他补充」的写回与撤销，这套逻辑用重型方案表达出来的配置成本高于手写自研渲染器，而且不好调试。自研渲染器已经在两版 Demo 里跑通。
- **不用 uni-app。** 能力与 Taro 等价，差别是 Vue 还是 React。选 React 是因为 AI 辅助开发时语料更厚。
- **不用 Taro 承载解读端。** Taro 唯一的优势是一套代码产出小程序与 H5，这个前提在解读端不成立；宽屏桌面是它的次要场景，用它反而要额外处理 rem 适配与路由。
- **不用纯静态 H5 直连模型。** 密钥会暴露在浏览器、CORS 要绕、脱敏无法保证。
- **不做多租户。** 只服务自己公司，把租户维度做进数据模型和仓储层，是在为不存在的需求付长期成本。
- **不上 Electron / Tauri 做桌面壳。** 产品是网页端；将来若有需求，把同一个 Web 工程打包即可。
- **不上微服务与 K8s。** 单体 API 服务足够支撑到这个体量。
- **不做境外模型与境外云。** 见 9.3。
- **不让展示版影响架构。** 展示版是 H5 产物的副产品，不为它单独设计代码结构。

### 2.5 唯一没有把握的地方

**现场端的离线同步本身**是全篇最没把握的一块：断网时产生的记录怎么排队、重连后怎么合并、同一条目在两台设备上都改过怎么办。这一块要在开工前用真机验证：

1. 断网下连续记 20 条，重连后一条不少；
2. 切后台、杀掉进程再回来，未同步的记录还在；
3. 同一条目两端都改时，不出现「结论被覆盖成空」。

验证不过就退到最保守的做法：现场记录一律只追加、不合并，冲突时两条都留，由设计师回公司选一条。

采集端侧另有一个已知的技术不确定点：**Taro 的主场是移动端 H5，用它承载宽屏 Web 是次要场景**，需要额外处理两件事——关闭 rem 适配改用 px 加媒体查询，以及宽屏下的路由与样式隔离。这一条已经在实现中验证过（见 6.10 的判定信号）。

## 三、架构分层

### 3.1 结构

```
┌──────────────────── 客户端 ────────────────────┐
│  问需 · 采集（Taro：weapp + h5）                 │
│  问需 · 解读（Next.js 桌面工作台）                │
│  问需 · 现场（Vite + React PWA，独立工程）        │
└───────────────────────┬────────────────────────┘
                        │  契约层 packages/contracts（zod → 类型 + OpenAPI）
┌───────────────────────▼────────────────────────┐
│  API 服务 services/api                          │
│  · 鉴权与角色                                    │
│  · 采集通道（房主提交，与内部通道隔离）            │
│  · 需求单 / 清单 / 现场记录 资源                   │
│  · 脱敏 → 模型调用 → 外发审计                     │
└───────────────────────┬────────────────────────┘
                        │
┌───────────────────────▼────────────────────────┐
│  领域层 packages/*（纯 TS，零框架依赖）           │
│  field-spec · rules · summary · data            │
│  checklist · redact · contracts · service        │
└───────────────────────┬────────────────────────┘
                        │
          Postgres · 对象存储 · DeepSeek
```

**分层纪律**：领域层不 import 任何框架、不读环境变量、不产生副作用；API 服务不自己写业务判断，只做编排与持久化；客户端不算业务结论，只做「读状态、渲染、派发事件」。这条纪律是整套方案能否成立的前提。

### 3.2 依赖方向

```
packages/*          不依赖任何东西
services/api        → packages/*
app（采集端）        → packages/*
studio（解读端）     → packages/* + contracts
onsite（现场端）     → packages/* + contracts
```

反向依赖一律不允许：领域包里出现框架 import、或 API 服务里出现界面判断，都要立刻停下修边界。

### 3.3 目标仓库结构

```
问需/
  app/                  # 采集端（Taro：weapp + h5；pwa/ 是手机版资产，只复制进 H5 产物）
  studio/               # 解读端 · 桌面工作台（Next.js）
  onsite/               # 现场端（Vite + React + PWA，独立工程）
  services/
    api/                # API 服务（多客户端共用）
  packages/
    field-spec/         # 字段规格（由字段清单 Excel 导出）、表单模型与校验
    rules/              # 规则引擎：命中、排序、去重、静默状态机、写回动作
    summary/            # 需求摘要与量房确认清单文本
    data/               # 草稿读写、版本迁移、提交与埋点
    checklist/          # 量房沟通清单：来源候选、判据筛选、合并去重、排序计数、导出
    redact/             # 外发脱敏：字段级三级策略、自由文本替换、外发 payload 与审计记录
    contracts/          # API 契约与共享类型（zod → 类型 + OpenAPI）
    service/            # 服务端纯逻辑：清单生成流水线、投影、模型接口
    devtools/           # 单测与类型检查用的开发依赖
  tools/                # 字段清单 Excel → JSON、Demo 构建脚本、部署脚本
  docs/                 # 产品设计文档与技术方案
  demo/  mobile/        # 采集端早期 Demo（交互设计稿）
  designer/             # 解读端与现场端的 Demo（交互设计稿）
  tests/                # 三层测试（领域单测 + API + 各端端到端）
```

`demo/`、`mobile/`、`designer/` 保留但不再演进：它们记录了三端的信息架构取舍，是各端实现时的参照物。

## 四、领域包

领域包是「各端行为不漂移」的唯一手段，也是整套架构里最该被保护的部分。

| 包 | 负责 | 关键约束 |
| --- | --- | --- |
| `field-spec` | 字段规格、表单模型、控件决策、校验 | 字段清单 Excel 是唯一的人类编辑入口，JSON 由脚本导出；字段 ID 一旦发布不做重命名 |
| `rules` | 发现规则：命中、优先级排序、去重、静默状态机、写回动作 | 计算接口是纯函数：输入表单快照，输出发现项数组，不读全局状态、不产生副作用 |
| `summary` | 需求摘要、量房确认清单文本、清单概览折叠 | 模板拼装，不调用模型；摘要在 150 字以内 |
| `data` | 草稿读写、schemaVersion 迁移、提交与埋点 | 仓储接口按「将来要接的能力」设计，接云端时只换实现 |
| `checklist` | 来源候选（规则与资产）、判据筛选、合并去重、排序计数、Markdown 导出 | 去重键是「空间 + 核实对象」的结构化键，不用文字相似度；模型与规则托底的推导项由调用方传入 |
| `redact` | 字段级三级策略、自由文本替换、外发 payload、审计记录 | 策略是入参不是常量，因此同一份需求单在不同策略下的结果都能单测 |
| `contracts` | API 契约与共享类型 | zod schema 是唯一来源：运行时校验、TS 类型、OpenAPI 文档都由它产生 |
| `service` | 服务端纯逻辑：清单生成流水线、视图投影、模型接口、规则托底 | 不 import 框架、不读环境变量（环境由 API 服务注入） |
| `devtools` | 单测与类型检查的开发依赖 | 只被测试与 CI 使用 |

**为什么 `service` 单独存在**：清单生成是一条流水线（取数 → 脱敏 → 外发留档 → 模型 → 校验降级 → 判据 → 合并 → 排序 → 落库）。这条流水线要在服务端跑，但它的每一步都是纯逻辑，所以放在包里、用注入的 repo 与 provider 拼起来——这样它在 Node 单测里能整条跑通，不需要起 HTTP 服务。

## 五、契约优先

### 5.1 一份契约

API 的请求与响应由 `packages/contracts` 里的 zod schema 定义，运行时校验、TypeScript 类型、OpenAPI 文档都由这一份产生（`GET /openapi.json` 直接生成，不存在「文档和实现两份」的问题）。四个客户端不各自维护类型，契约变更由编译与测试兜住。

### 5.2 需求单契约

需求单是整条链路上唯一跨端的业务对象，它的契约就是产品文档 5.1 说的那份 JSON：

```ts
DemandSheetImport = {
  schemaVersion: string     // 字段清单版本；读入时按它做一次规范化
  submittedAt: string
  source: 'file' | 'miniapp'
  demandName: string        // 采集端不收集姓名，由导入的人写一个便于识别的叫法
  form: {
    values: Record<string, string | number | string[]>
    instances: Record<string, Array<{ key, section, values }>>
  }
  aiMarks: string[]         // 助手建议写入的字段，界面上标「助手建议」
}
```

文件导入与云端提交是同一个接口的两种输入方式：`source` 区分来源，`form` 与 `aiMarks` 的语义完全一致。

两条路现在两端都通了：

| 路 | 房主端 | 设计师端 | 来源 |
| --- | --- | --- | --- |
| 云端提交 | 提交设计师 → 采集通道 `/a`（有网时） | 列表里直接出现 | `miniapp` |
| 交接文件 | 提交前检查里的「存交接文件」：H5 下载一份 `.json`，小程序端退成复制 JSON（没网、或这套产物没接服务端时） | 「导入」：选文件或粘贴 JSON，当场过契约 | `file` |

两端用的是同一份结构（`packages/data` 的 `buildSubmission`），所以「房主存下来的文件」与「提交到通道的那一份」只差递送方式；`tests/api` 里有一条用例直接拿前者的文本走后者那条导入接口，卡住这个接缝。

### 5.3 采集通道与内部通道分离

房主不是用户（产品文档 8.6 与解读端的账号口径），所以采集端提交走的是另一条通道。这条通道已经开起来了（A4），两条通道的边界在**路由层**就分开，而不是靠业务代码里的判断。

| 通道 | 落点 | 鉴权 | 能做什么 |
| --- | --- | --- | --- |
| 内部通道 | `services/api/src/app.ts` 里 `/a` 以外的路由 | 内部 token：`TOKEN_SECRET` 签名 + `role` 控权限，`POST /auth/login` 换 | 文件导入（`POST /demand-sheets`）、读所有需求单、生成清单、导出、现场记录、账号管理 |
| 采集通道 | `services/api/src/collection.ts`，挂在 `/a` | 匿名会话令牌：`COLLECTION_SECRET` 签名 + `scope: 'collection'`，`POST /a/session` 换 | 只有两个写入口：`POST /a/session`（换会话）与 `POST /a/demand-sheets`（提交需求单）。**没有任何读接口** |

四条实现约定：

1. **令牌互不通用。** 两套签名用两把钥匙，payload 里各带一个 `scope`：拿会话令牌调内部接口是 401，拿内部 token 调采集通道也是 401（`tests/api/api.test.ts` 卡住这条）。房主的数据对外因此是结构性不可读的。
2. **来源由通道决定，不看客户端怎么写。** 走 `/a` 的一律记 `miniapp`（客户端在请求体里写 `file` 也没用），`submitted_by` 留空——房主不是用户，需求单里不记账号；走内部通道 `POST /demand-sheets` 的一律记 `file`（桌面端的文件导入，客户端写 `miniapp` 也不作数），`submitted_by` 是导入的那名内部人员。采集端也不收集房主姓名，所以落库的名字是契约默认的「未命名需求单」，由设计师在桌面端改成认得出的叫法（6.12 的改名入口）。
3. **幂等靠 `submissionId`。** 采集端每提交一次生成一个 id，弱网重试带的是同一个；服务端认出是同一份就不再落第二份，回执里 `replay: true`。重放的回执只回客户端自己带上来的值，不回库里的那一行——这条通道没有读接口，回执也不能变成读数据的一个口子。
4. **这条通道上没有别的接口。** 除上面两个写入口，`/a` 下任何路径都回 404（含 GET）：兜底写在这条子应用里，而不是让请求漏到内部通道的守卫上——那样返回的「未授权」就把边界从路由层滑回了业务层。

采集端那一侧跟着改了两件事：提交的内容从摘要文本改成结构化需求单（`packages/data` 的 `buildSubmission`，形状与 `DemandSheetImport` 一致），埋点随这一次提交整批上报；草稿仍然只存本机。H5 产物没配 `COLLECTION_API_BASE` 时是演示模式——照常走完全流程，提交只落本机，提示里说清楚，不假装送达。

**上线前置**：H5 从静态托管提交时是跨域请求，需要 CORS 白名单与限流（见第十二章待定项）。

### 5.4 字段清单版本与规范化

字段清单 Excel 是唯一的人类编辑入口，构建脚本导出为 `packages/field-spec` 的 JSON，服务端与四个客户端引用同一份。需求单带 `schemaVersion`，读入时按版本做一次规范化。

原则：**版本对不上时不静默丢弃。** 未知字段保留原值，在界面上标注「字段清单已更新」，让设计师看得见差异。版本升级的唯一来源是产品文档 7.3 的回路 C（字段增删）。

### 5.5 账号与权限

单组织，没有租户表，只有用户与角色：

| 层 | 含义 |
| --- | --- |
| 身份 user | 一名公司内部人员（设计师或管理员） |
| 角色 role | 管理员（管账号、管字段清单版本）/ 设计师（导入、生成、导出、现场记录） |

三条当前口径：

1. **房主不是用户。** 房主通过采集通道提交需求单，不进入账号体系（见 5.3）。
2. **同公司内默认可见。** 数据默认全员可见、操作留痕（谁导入、谁生成、谁导出、谁删减都记录在案）。若要求「只能看到自己负责的客户」，加一个 `owner_id` 过滤即可，不需要改结构。
3. **未授权访问不返回任何数据。** 除了健康检查、契约与登录，一律先过 token；测试里有一条专门守这条（见 8.2）。

将来若要按门店或分部划分，用一个可空的 `team_id` 表达即可，不必引入完整的租户体系。

## 六、关键设计

### 6.1 字段规格：单一来源

字段清单 Excel 是唯一的人类编辑入口，构建脚本把它导出为 `packages/field-spec` 的 JSON，前端渲染、规则引擎、清单判据、摘要生成、导出全部引用同一份数据。

```json
{
  "id": "kt_hood",
  "section": "厨房", "group": "油烟与灶具",
  "label": "油烟机形式", "type": "单选",
  "options": ["顶吸", "侧吸", "集成灶"],
  "suggest": "选填", "scope": "固定", "applies": "全部"
}
```

`scope` 区分固定分区与空间实例分区，`applies` 描述房型适用性，`suggest` 是填写建议（推荐填写 / 实例必选 / 选填）。字段 ID 是前端数据键，一旦发布不做重命名。

配套的 16 项通用量房确认清单是同一份资产的一部分，带机器可读的 `related_fields: string[]`，因此它的触发判断可以用规则引擎做，不需要模型。

还有一份更小的资产：`unclear-checklist.json`，装「房主答『不清楚 / 听设计师建议』时量房要问的那条」。采集端只在 9 个涉及专业判断的字段上给这个选项，其中 3 个（房屋现状、空调、采暖）本来就能落到通用清单上，剩下 6 个各配一条。两份资产都由单测卡住：字段清单变了、选项变了，测试会要求回来重新决定，不会悄悄漏掉。

### 6.2 字段渲染：元数据驱动

渲染器接收「字段定义 + 当前值 + 是否带助手标记」，输出对应控件。三类控件覆盖全部 191 个字段：选项组（单选 / 多选）、输入（文本 / 数字 / 日期）、长文本。

渲染决策（出哪种控件、可选项是什么、是否显示）是纯函数，放在 `field-spec` 里用 Vitest 测；真正的渲染实现很薄，按端各写一份。

### 6.3 规则引擎

规则分两部分：

- **元信息**（可序列化）：`id`、优先级、发现类型、目标字段、写入动作、文案模板、依据模板。
- **谓词**（触发条件）：判断当前表单快照是否命中，并给出发现项。

谓词用 TypeScript 承载，因为它需要按空间实例展开（例如「任一卫生间选了浴缸 → 针对该实例生成一条发现」），纯声明式结构表达不了。计算接口保持纯函数形态：输入表单快照，输出发现项数组，中间不读全局状态、不产生副作用。

为了让规则能在不发版的前提下调整，接口层面预留云端覆盖：规则元信息与谓词标识从远端读取，命中判断仍在客户端执行。这一版先内置，接云端时不改调用方。

执行时要保证的四件事：

1. 同一条发现在一次会话中只出现一次；
2. 风险提醒被「保持需求」后不再重复出现；
3. 发现项按 P0 → P1 → P2 排序，风险提醒优先；
4. 连续 3 次「不感兴趣」进入静默，静默状态只属于本次会话。

### 6.4 状态与草稿

采集端的状态是一棵可序列化的树，包含四部分：表单值（固定字段与各空间实例）、发现处理状态、静默与计数、结构版本号。

整棵树序列化后写入本地存储，读回时按 `schemaVersion` 做迁移。字段清单升级（增删字段、改选项）时必须保证旧草稿可读——这是唯一需要版本迁移机制的地方。

### 6.5 清单在服务端生成

产品文档 5.3 的来源分工不变，落地位置明确如下：

| 来源 | 谁做 | 在哪 |
| --- | --- | --- |
| 空缺的推荐项 | 规则 | `checklist` 包，进表格理解的待确认项 |
| 答「不清楚」的项 | 规则 | `checklist` 包的 `unclearCandidates`，**进清单候选**：能落到通用清单的并成一条，落不到的用 `field-spec` 的待定项资产 |
| 规则命中的高信号发现（养猫、有老人、中央空调…） | 规则托底 | `service` 的 `rule-candidates`：把命中转成 `DerivedItem`，与模型输出一起进 `checklist` 的判据与合并 |
| 字段之间的矛盾（预算与面积、工期与定制周期） | 规则 | `rules` 包，已有 |
| 从已填内容推导「要问什么、为什么问」 | 模型（DeepSeek） | 服务端 adapter |
| 16 项通用量房清单 | 现成资产 | `field-spec` 的通用清单 JSON（已补 `related_fields`） |

判据筛选（产品文档 5.4）、合并（5.5）、排序与计数（5.6）全部落在 `checklist` 包，是纯函数，可单测。

**规则托底为什么放在 `service` 而不是 `checklist` 包**：它要同时认规则库（`ruleId`）与字段清单（`fieldIds`），而 `service` 本来就把两者都当依赖；放进 `checklist` 会让领域包多一条指向 `rules` 的边，还要给三个客户端多带一份规则库。转换出来的形状与模型输出完全一致（`DerivedItem`），所以判据、合并、排序、导出都不用改一行。

**实测补上的三条实现约定**（产品文档 5.5 的产品侧结论，这里是实现落点）：一、**核实对象命名要对齐**——把资产里的 16 个核实对象名作为固定前缀交给模型，不对齐时实测一条都并不上；二、**分区以资产为准**——与资产同名的核实对象，归属分区一律取资产声明的那一个，不随模型给字段的先后顺序漂移；三、**对象名归一**——名字仍旧会在代码里过一道（`checklist` 的 `objects.ts`，badcases.md BC-05）：与某个资产对象互相包含（「厨房排烟」↔「排烟」、「封窗」↔「家政封窗」、「猫砂盆」↔「猫砂盆位置」）或命中别名表（「上水下水」→「上下水」）时归到标准名，**只在唯一命中时才归**，复合名与歧义名（「上下水与排烟」「中央空调」）并列两条。归一用的资产清单是通用清单 + 待定项资产 + 调用方传入的额外资产：规则托底那几条的标准名由 `service` 的 `ruleObjectAssets` 按需求单算好（实例规则的分区是算出来的，「次卧1 · 儿童房」不能只按名字给），经 `buildChecklist({ objects })` 传进领域包。三条都落在 `packages/checklist` 的纯函数里，带回归测试。

模型只负责推导问题与依据，输出必须附字段 ID；指不到字段的只能标为「来自通用量房清单」。

**生成放在服务端的三个理由**：模型调用本来就必须在服务端；外发记录要求可审计可复现；三个客户端拿到同一份清单，不会因为各自计算而分叉。一次生成是一条完整流水线，失败时不落半成品清单。

### 6.6 脱敏与外发：顺序即安全

产品文档第八章的「本地处理」，在服务端化之后含义变为**自有服务端**。安全边界没有变：房主数据不许离开自有系统去第三方模型。顺序不能颠倒：

```
客户端勾选要外发的字段（F3）
      ↓
服务端按需求单取数（含不勾选的字段，用于本地规则计算）
      ↓
redact 包执行脱敏：不外发字段整条剔除；可泛化字段本地降级；自由文本先替换
      ↓
写入外发审计记录（字段清单 + 脱敏命中位置 + 策略版本 + 时间 + 操作人）
      ↓
调用 DeepSeek
      ↓
落库生成清单
```

三条硬约束：不外发字段不进任何请求；外发必须经设计师逐条确认；外发记录事后可查。

**策略是可配置的数据，不是代码常量。** `redact` 包把策略作为入参（纯函数，因此同一份需求单在不同策略下的结果都能单测）；默认策略集随代码发布并带版本号，公司按合规口径调整时只改策略数据。每次外发记录与当次生效的策略版本一起落库——否则审计还原不出当时的口径。

### 6.7 模型接入（DeepSeek）

接口在领域层定义，实现在服务端：

```
provider.understand({ fields, task }) → {
  profile, demands, conflicts, toConfirm,      // 表格理解四块
  derivedItems: [{ question, why, onsiteChecks, relatedFieldIds }]
}
```

七点要求：

1. **用 JSON Output，不解析自由文本。** 官方 API 是 OpenAI 兼容的，用它的结构化输出模式，并在提示词里把返回结构与示例写清楚。
2. **返回后必须过 zod 校验，两道红线。** 结构不合法，或出现字段清单之外的 `fieldId`，一律判为失败；重试仍失败则降级为纯规则清单，并在该需求单上标明「模型部分未生成」。**宁可少，不可编。**
3. **测试用 fake provider。** 生成流程的单测不依赖真实模型；真实模型的效果实测单独跑（`pnpm run measure:model`）。服务默认 `MODEL_PROVIDER=fake`。
4. **型号定案为 `deepseek-chat`。** 三个种子场景各跑一轮的实测结果：非推理型号 3.9–18.6 秒、18 次调用里 1 次降级（默认输出上限把 JSON 截断，已由 `max_tokens` 与 `finish_reason` 校验修掉，修后未再复现）；推理型号 17.7–70.3 秒、8 次调用里 2 次降级（一次是连接中途断开，一次是把 JSON 裹进代码块，已加容错）。结构化抽取用非推理型号：输出更稳，延迟与成本低一个量级。
5. **缓存两层。** 结果按「需求单 + 字段清单版本 + 勾选集合」缓存；同时把系统提示词与字段清单固定放在请求前缀，以命中官方的前缀缓存、压低重复调用成本。
6. **超时、重试与可中断。** 生成是一次长任务（目标 ≤ 5 分钟），界面要有进度与中断，失败可重试且不产生半成品。
7. **输出上限要显式给足。** 官方默认的输出上限会把长需求单的 JSON 截断（截断时 `finish_reason=length`），生成会直接落进降级；adapter 显式设置 `max_tokens`，并在截断时抛出可诊断的错误，而不是把半截 JSON 当成「结构不合法」。
8. **清单质量有独立的评估口径。** `evals/` 下是评分器、13 个用例（3 个种子 + 10 个边界）、离线回归门禁与 badcase 台账；每次改动跑离线回归，换型号或改提示词跑真机实测（`pnpm run eval:model`，顺带出成本口径）。多批真机实测（`deepseek-chat`，每批 13 个用例各 3 次）的结果：零越界字段（「不编造」这条红线在真实模型上守住）；单份解读约 11 秒，远低于上面第 6 条里 5 分钟的目标；条目集合稳定（Jaccard 0.83–1.0），但**必问档位在 7–21 条之间飘**，这是把档位收回到代码的直接依据（产品文档 12.1、待定项 8）。adapter 留了 `onUsage` 钩子，接上埋点就能在生产里盯调用用量。

### 6.8 摘要与输出物

需求摘要由模板拼装已填字段与已确认的发现，不调用模型，长度控制在 150 字以内。摘要是纯函数，放在 `summary` 包里。

量房沟通清单由服务端生成，导出为 Markdown 或可复制文本；现场端的量房记录同样可以拼成一份速记。两份文本的拼装逻辑都在 `checklist` 包里，不放在界面层。

### 6.9 回流的数据落点

产品文档第七章定义的回流闭环，在技术上的落点如下。

| 证据 | 落点 | 现状 |
| --- | --- | --- |
| 设计师删减 | `checklist_items` 上的可撤销标记，带操作人与时间 | 已实现（含撤销接口） |
| 现场记录 | 独立的现场记录表：客户端生成的 uuid、条目的稳定标识、状态（已问 / 没问上）、一句话结论或原因、记录时间 | 已实现；与清单**分表**，重新生成清单不覆盖它 |
| 遗漏补录 | 人工写入口，归入「遗漏台账」 | 已实现：桌面端清单页底部补录一条（分区 + 归类 + 一句话），落成 `omission_log` 事件；台账与其余三张报表见 6.12 |
| 房主拒绝 | 采集端埋点 → 采集通道上报 | 已接通：`ignore` 事件带规则（见 6.11），随提交整批进 `events` 表，规则健康度直接读它 |

三条实现约束：

1. **清单条目的稳定标识不带分组**，用「核实对象 + 主要来源字段」。分组会随产品判断调整（已经改过一次），标识跟着分组走的话，改一次分组、重新生成一次清单，现场记录就断了。
2. **清单与现场记录分表。** 清单是生成物，记录是资产——是「清单有没有用」的唯一证据，不能被重新生成覆盖掉。
3. **报表只汇总，不回改。** 服务端只做四张口径的汇总查询（产品文档 7.6：规则健康度、判据健康度、字段健康度、遗漏台账），任何「自动下架某条规则」的逻辑都不进这一版。

### 6.10 跨端分支的边界

**采集端**允许分支的地方只有三个壳组件：

| 壳组件 | 宽屏（Web） | 窄屏（小程序 / 展示版） |
| --- | --- | --- |
| 表单容器 | 多列网格，大类可同时展开 | 单列，手风琴一次只开一个 |
| 助手容器 | 右侧常驻侧栏 | 底部常驻横条 + 半屏弹层 |
| 分区导航 | 竖直进度点 | 顶部横滑胶囊 |

**解读端与现场端**允许分叉的地方只有三处：导航结构、清单呈现方式、输入方式。必须共享的是领域逻辑（`packages/*`）与接口契约（`contracts`）；状态层与 UI 组件各写各的——两个工程、两个运行环境，硬共用状态层反而互相牵制。

**判定信号**：一旦业务判断开始出现在某个端的渲染代码里（比如单个字段控件里出现平台判断，或某个工程自己写了一份判据），说明逻辑没有沉到包里，应当先停下来重构，而不是继续加分支。

### 6.11 指标口径与埋点

产品文档第十章的每个指标在这里定清「从哪来」。两条原则：

1. **一张表一件事。** 只给「没有别的表能承载」的动作埋点：清单删减与现场记录各自有表（`checklist_items` / `site_records`），指标直接读表。同一处事实只有一个来源，也不会出现「事件表与业务表对不上」时不知道信谁。
2. **名字只有一份清单。** 事件名与每个事件带的字段定义在 `packages/data` 的 `events.ts`：采集端照它记录，服务端用同一份清单校验上报体（`contracts` 的 `EventBatch`），契约文档与指标取数也认它。名字写错就是一份口径不明的数据。

事件清单：

| 事件 | 谁记 | 什么时候 | 带什么 | 喂哪个指标 |
| --- | --- | --- | --- | --- |
| `session` | 采集端 | 打开填写页，一次会话一条 | `env`、`narrow` | 填写时长、装机率、静默触发率的分母 |
| `shown` | 采集端 | 助手发布了一条新发现（会话内同一条只记一次） | `rule`、`target`、`kind` | 发现采纳率与不感兴趣率的分母 |
| `adopt` | 采集端 | 采纳 | `rule`、`target` | 发现采纳率的分子 |
| `ignore` | 采集端 | 不感兴趣 | `rule`、`id` | 不感兴趣率的分子；回路 A 的输入 |
| `keep` | 采集端 | 保留房主原需求 | `rule`、`id` | 区分「没理」与「明确不要」（观测项） |
| `quiet_on` | 采集端 | 进入静默（人工，或连续 3 次不感兴趣） | `trigger` | 静默触发率 |
| `install` | 采集端 | 手机版被加到主屏幕（H5 的 `appinstalled`） | — | 装机率 |
| `submit` | 采集端 | 提交 | `length` | 填写时长的终点 |
| `checklist_generate` | 服务端 | 生成一份清单 | `durationMs`、`degraded`、`model`、`items`、`must`、`suggest` | 单份解读耗时、降级比例 |
| `checklist_export` | 服务端 | 导出清单 | `items` | 「生成了却没导出」的断点 |
| `omission_log` | 服务端（桌面端补录） | 量房结束后补一句「该问而没列」 | `space`、`category`、`note` | 遗漏率、遗漏台账 |

**落点**：`events` 表（`services/api/src/db/schema.sql`）——需求单、事件名、发生时间、来源（client / server）、操作人、`batch_id` + 批内序号、`props`。

**上报与幂等**：采集端的埋点先攒在本机草稿里（上限 200 条），随提交或断网重连整批上报 `POST /demand-sheets/{id}/events`；幂等靠 `batchId` + 批内序号，重试的是整批而不是单条，这正好是真实的失败形态。服务端另给一个查询接口（`GET` 同一路径，`audit:read`），指标就是拿它算的，出问题也能顺着看到原始事件。

**房主那条通道（A4 采集通道）已经开了**（5.3）：采集端提交时把这一批事件放进 `DemandSheetImport` 的 `telemetry` 字段一起发，服务端校验与落库的那一段两条通道共用——通道只换了鉴权与来源。落库后事件不会重复计数：同一个 `batchId` + 批内序号的整批重发只落第一次，而采集端在提交成功后就把这一批从草稿里清掉，不会换个批号再报一遍。内部 token 那条 `POST /demand-sheets/{id}/events` 仍然留着，给内部人员与文件导入补报用。

**采集端已经攒下来的**：`session` / `shown` / `adopt` / `ignore` / `keep` / `quiet_on` / `install` / `submit` 全部落在本机草稿里。这里踩过一个坑值得记下——事件的保存路径与草稿的保存路径原来是两条（一条直接写存储、一条整份写回），结果是**表单一动，事件就被盖掉**：采纳、忽略、示例填充之后事件全没了。现在事件与表单各写各的：事件并进草稿后由同一条路径落盘，表单动作不再覆盖事件（`app/src/store.ts` 的 `trackEvent` 与 `commit`，`tests/app.e2e.mjs` 卡住这条）。

**服务端已经接上的**：生成清单时记 `checklist_generate`（墙钟耗时、是否降级、模型名、条目 / 必问 / 建议问条数），导出时记 `checklist_export`。adapter 的 `onUsage` 钩子留给将来接 token 用量，本版不记。

**已经接上的**：`omission_log`——桌面端清单页底部补录一条（分区 + 归类 + 一句话），走内部通道的 `POST /demand-sheets/{id}/omissions`，落成一条 `omission_log` 事件；台账就是这些事件本身，不另起一张表（同一处事实只有一个来源）。

### 6.12 回流报表的四张口径

产品文档 7.6 的四张报表落在 `packages/service` 的 `reports.ts`：一个纯函数 `buildReports(store)`，输入是几个读能力（列需求单、取最新清单、列现场记录、列事件），**汇总逻辑不在路由层**（3.1 的分层纪律）。服务端只多了 `GET /reports` 一个读接口（`audit:read`）。

四张表各自的口径与取舍：

| 报表 | 分子 / 分母 | 这一版的取舍 |
| --- | --- | --- |
| 规则健康度 | 采纳数、不感兴趣数 / **展示数** | 分母是展示数不是采纳数：没人看到的发现不该算它被拒绝。一次都没展示时拒绝率是 null，界面显示「—」 |
| 判据健康度 | 被删条目数 / 条目数，按**来源 · 档位**分组 | 条目上没有存它满足了哪条判据（判据只在筛选那一刻用一次），所以按来源（需求推导 / 通用核实 / 推导+通用）与档位分组——同样回答「哪类条目最常被删、档位是不是定错了」。要精确到判据，得先把 `impact` 落到条目上，那是领域包与表结构一起改的事 |
| 字段健康度 | 答「不清楚」的需求单数 / 有值的需求单数；被标「没问上」的条目数 / 引用到该字段的条目数 | 两个来源各算各的分母，不混成一个率。同一条清单条目引用多个字段时，在这几个字段上各算一次，否则「一条问三件事」的条目会把分母算少 |
| 遗漏台账 | 人工补录的条数 | 按分区与归类排，归四类：模型推演 / 通用清单 / 字段清单 / 说不清——前三类各指向一条回路的改动落点 |

三条实现约定：

1. **只算每份需求单最新那一份清单。** 重新生成过的旧清单不再计入，否则「生成三次、删一次」会把同一条条目数成三条。删减取条目的当前状态，撤销后不计入被删（7.5 第 2 条）。
2. **率一律是百分数，分母为 0 时是 null。** 界面把 null 显示成「—（还没有样本）」，把没有来源的列显示成「未采集」——两者都不是 0%。这一版没有来源的列只有一处：**现场修正率**（现场记录只标「已问 / 没问上」，没有「结论与房主原填不符」的落点），它随报表一起返回在 `unavailable` 里说明原因。
3. **实时查询，不落汇总表。** 待定项 6 收敛为实时：数据量是「几份需求单、几十条条目」，落一张汇总表是提前优化；真到要按周看趋势时再加。

报表之外，桌面端还多了一个改名入口（`PATCH /demand-sheets/{id}`）：采集端不收集房主姓名，房主提交的需求单落库叫「未命名需求单」，由设计师改成「张先生 · 89㎡ 老房翻新」这类认得出的叫法。改名只动名字，房主填的内容一个字不变（待定项 9 收敛为「设计师端加改名」）。

## 七、工程原则：把逻辑放在能自动验证的地方

这是本项目最重要的一条工程约束，其他细节都可以让步。

小程序端没有稳定的自动验证手段：AI 改完代码无法自己跑起来看结果，只能依赖人在开发者工具里确认。Web 端相反，无头浏览器可以完整跑通流程并截图。所以架构上要主动把逻辑从渲染层挤进领域层：

- 规则命中、优先级排序、去重、静默状态机、摘要生成、字段校验、草稿迁移；
- 清单判据、合并去重、排序计数、Markdown 导出；
- 脱敏替换、外发 payload 组装、审计记录；
- 字段规范化、模型返回的校验与降级。

以上全部是纯函数，在 Node 里用 Vitest 跑。呈现层只做「读状态、渲染、派发事件」，越薄越好。目标是把**无法自动验证的代码占比压到最低**——这条原则对解读端与现场端更重要，因为它要同时服务三个客户端。

### 8.2 必须守住的验证点

- 规则与清单引用的字段 ID 必须存在于字段清单（防止字段清单与规则漂移）；
- 字段清单注入的字段数量与 Excel 一致；
- 外发 payload 中不出现标为「不外发」的字段值——**误发即失败**；
- 每条清单项可溯源：要么有字段 ID，要么标为来自通用量房清单——**编造即失败**；
- 模型返回中出现字段清单之外的 `fieldId` 时，生成必须失败并降级；
- 未授权访问不返回任何数据；
- 字段清单升级后，旧需求单与旧草稿仍可读；
- 采集端 H5 产物必须带手机版四个资产（`manifest.webmanifest`、`sw.js`、两个图标），且**不出现**在小程序产物里；
- 手机版 manifest 的名称用问需体系，service worker 必须能注册成功——装机能力坏掉要立刻发现，而不是等房主装不上；
- 直接打开构建模板文件不能出现空白页或 NaN；
- 控制台无错误。

## 九、构建、部署与合规

### 9.1 构建

**字段数据**：改字段清单 Excel 后运行构建脚本导出 JSON，禁止手工编辑导出结果。字段清单 JSON 属于代码资产，随代码一起发布，不走环境变量。

**采集端**：H5 与小程序两个产物由同一套代码构建；H5 产物部署为静态站点，宽屏即 Web 端，窄屏即手机版。H5 端不使用任何小程序专属 API。

手机版的四个资产（`manifest.webmanifest`、`sw.js`、两个图标）放在 `app/pwa/`，由 Taro 的 `copy` 只复制进 H5 产物，不污染小程序产物。service worker 采取**文档请求网络优先**：房主可能今天填一半、过几天回来接着填，缓存优先会让它一直看到旧版本；带哈希的静态资源仍走缓存优先。

小程序产物由 `pnpm run build:weapp` 产出到 `app/dist/weapp/`，用微信开发者工具打开 `app/` 就能预览或上传。`project.config.json` 里的 `appid` 目前是 `touristappid`（测试号）：要面向用户发布，得换成公司自己的 appid 并走类目与隐私协议提审。手机版不需要这一步，所以两条路可以各自推进。

**解读端**：Next.js 构建并导出静态产物；本地开发用 `next dev`，测试用 `next start`。

**现场端**：Vite 构建，产物是静态文件 + service worker + manifest；手机上装到主屏幕即可离线打开。

**小程序端**：微信开发者工具上传。上线前要准备的合规项包括类目（工具）、隐私协议声明、用户填写内容的收集说明。个人主体不能获取手机号，产品设计上不要依赖它。

### 9.2 部署形态

Docker 镜像 + 公司自己的服务器或境内云主机 + 托管 Postgres + 对象存储。静态产物可以放在任意静态托管上（Cloudflare Pages / GitHub Pages / 自有 Nginx），两个设计师端在没有 API 时走演示模式：判据、脱敏、合并、排序仍然是 `packages/*` 里那份真代码，只有存储与模型换成浏览器内的实现。

当前线上发布的就是这一条的静态部分：入口页、采集端（含手机版）、解读端与现场端四个入口，同一份产物同时发布到 Cloudflare Pages（`demand-studio.pages.dev`）与 GitHub Pages（`xinhao021121-web.github.io/zhuangxiu-demand`），互为备份。API 服务还没部署，因此两个设计师端目前跑的是演示模式。发布流程、缓存策略与两个托管的差异见 `deploy/README.md`。

这里有一个容易忽略的连带影响：**设计师要在量房现场用手机访问，就必然要走公网**，那就需要域名与 ICP 备案；如果接受只在公司内网使用，可以省掉备案，代价是现场端实际上用不了，只能导出纸质清单带出门。

### 9.3 境内与数据边界

- 服务、数据库、对象存储与模型全部在境内，DeepSeek 官方 API 在国内可直接访问；
- 房主信息在采集端要做明确告知与同意；
- 每次外发 DeepSeek 都留档，满足「事后可查」；
- 密钥走环境变量，不进仓库、不进前端。模型既可用官方接口，也可换成私有化部署（API 形态一致，只换 adapter 实现，切换不动上层）。

**房主数据发给第三方模型服务，在合规口径上属于委托处理。** 口径由公司定，产品侧两条路都留：官方 API 是最省事的默认；私有化部署让数据完全不出内网，代价是 GPU 与运维成本。不必现在锁死。

### 9.4 环境

开发、预发、生产三套环境，数据库与对象存储分开。API 服务的环境变量包括端口、数据文件路径、token 密钥与有效期、内部验证码、模型提供方与密钥、模型接口地址与型号、模型接入方式（官方 / 私有化）。

## 十一、风险与退路

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| Taro 扛不住宽屏 Web | 宽屏布局需要大量平台判断才能实现 | 拆成两套界面 + 共用一个领域包 |
| 布局分支渗透进字段层 | 单个字段控件里出现平台判断 | 同上，不要继续加条件编译 |
| 小程序端长表单性能不足 | 真机上展开大类时卡顿 | 加深分包与懒渲染；必要时按大类拆页面 |
| 个人主体类目受限 | 提审被要求补充资质 | 收紧名称与简介表述，向「工具」靠；必要时调整上线计划 |
| 手机版装到主屏幕后看到旧版本 | 房主跨天回来发现界面与上次对不上，或一直停在旧版 | 文档请求走网络优先（缓存优先只留给带哈希的静态资源）；service worker 的缓存名带版本号，升级时旧缓存整体清掉 |
| 依赖框架导致返工 | 领域包里出现框架 import | 立即停下修边界，这是分层的底线 |
| 模型输出编造或不可溯源 | 单测或线上出现无字段 ID、或字段清单之外的 ID | 收紧提示与校验，失败重试，仍失败则降级为纯规则清单 |
| DeepSeek 高峰延迟或限流 | 单份解读耗时明显超过 5 分钟 | 超时与重试、生成异步化、结果缓存；必要时换型号 |
| 结构化输出不稳 | 返回结构不合法比例偏高 | 明确 JSON 模板与示例，扩大重试，保留规则兜底 |
| 数据外发口径收紧 | 公司要求房主数据不出内网 | 私有化部署 DeepSeek 开源模型，只换 adapter |
| 三个前端工程的维护成本 | 同一处改动要在三个工程各改一遍 | 逻辑继续沉在 `packages/*`，呈现层只做渲染；跨端一致的行为由领域包的单测兜住 |
| 清单变长导致设计师大量删减 | 清单可用率低于目标 | 回去调判据，不设条数上限（产品文档 5.6 已定） |
| 调用成本超预期 | 单份解读的调用次数或 token 过高 | 已实测（`evals/report-cost.md`）：单份 **1.08 次调用、2085 输入 + 2473 输出 token、前缀缓存命中 90%**，按示例价约两分钱一份，占装修客单价的十万分之一量级——成本不是约束（换算与盈亏平衡见 `research/问需_成本与ROI模型_V1.md`）。缓存与稳定前缀继续保留，但它们的价值在提示词稳定与可复测，不在省钱 |
| 现场端离线冲突 | 断网记录重连后出现覆盖或丢失 | 退到最保守做法：只追加、不合并，冲突时两条都留（2.5） |
| 回流证据不足 | 报表样本量太小，看不出结论 | 先取基线不做自动下架（产品文档 7.5）；把遗漏补录做成人工习惯的一部分 |

退路始终有效，因为领域包与框架无关——这是把它抽出来的主要目的。

## 十二、待定项

| # | 内容 | 影响 |
| --- | --- | --- |
| 1 | 采集通道的鉴权形态：**已定为匿名会话**（小程序还没有自己的 appid，拿不到 code）。有 appid 之后可以改成微信登录换 session——只是把 `POST /a/session` 的入参从空换成 code，路由与权限结构不动（5.3） | 影响采集端隐私告知的写法 |
| 2 | 上线时 DeepSeek 走官方 API 还是私有化部署 | 两者都支持、可随时切换，上线前按公司合规口径定一次 |
| 3 | 设计师端登录方式（手机号验证码 / 企业微信扫码） | 影响账号体系与邀请流程 |
| 4 | 同公司内是否要按负责设计师隔离（默认全员可见） | 默认已定：全员可见 + 操作留痕；要隔离时加 `owner_id` 过滤，不改结构 |
| 5 | 是否走公网部署（决定要不要备案，也决定现场端能否使用） | 影响部署清单与现场端的价值 |
| 6 | 报表的计算方式：**已定为实时查询**（数据量小，落汇总表是提前优化，见 6.12）。要按周看趋势时再补汇总 | 影响数据量假设与后续的看板 |
| 7 | 遗漏补录的入口位置：**已定为桌面端**（清单页底部，与台账、报表在同一处）。现场端收尾再补一个入口随时可加——接口是同一条（6.12） | 影响设计师什么时候补这一句 |
| 8 | 采集通道的 CORS 白名单与限流（H5 从静态托管提交时是跨域请求，匿名会话的地址是公开的） | 影响 H5 形态能否真正接上服务端；限流口径与公司合规口径一起定 |
| 9 | 采集端提交的需求单没有可识别的叫法：**已定为给设计师端加改名**（`PATCH /demand-sheets/{id}`，6.12）。采集端仍然不收集姓名，房主端少问一句 | 影响设计师在列表里认不认得出这是谁家 |
| 8 | 必问档位的口径 | 口径定了才能把档位从模型手里收回到代码（产品文档 12.1） |
| 9 | 宽屏 H5 的断点与栅格方案 | 影响采集端表单容器的实现 |
| 10 | 规则元信息的云端承载形态（自建配置还是云开发数据库） | 影响 6.3 的覆盖机制 |
| 11 | 指标看板的其余部分 | 埋点字段与落点已定（6.11），7.6 的四张报表已实现（6.12）；第十章里填写时长、装机率、静默触发率、单份解读耗时这些还没有汇到一处，看板做不做、做成什么样待定 |
| 12 | 是否需要对象存储（导出件是否落对象存储） | 影响部署清单与权限模型 |
| 13 | 微信小程序的 appid 与提审（现在还是测试号 `touristappid`） | 决定采集端能否在微信里上线；不发布也不影响手机版可用 |

**已定**：产品名「问需」与三个端名；只服务本公司、不做多租户（原待确认项已结）；外发策略（含自由文本默认值、模型接入方式）可按公司合规要求调整；现场端是独立 PWA 工程，与桌面端共用领域包与契约、不共用构建；型号定案为 `deepseek-chat`，输出上限显式给足，截断按可诊断错误处理。
