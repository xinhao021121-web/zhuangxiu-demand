## 一、目标与范围

### 1.1 要支撑的形态

| 形态 | 载体 | 阶段 | 定位 |
| --- | --- | --- | --- |
| 采集端小程序 / H5 | 房主手机、房主电脑 | 已有 | 正式产品；后续改为提交到云端 |
| 解读台 · 桌面工作台 | 设计师电脑浏览器 | 本版 V1 | 公司内部工具：导入 → 确认外发 → 表格理解 → 清单 → 导出 |
| 解读台 · 现场流程（独立 PWA 应用） | 设计师手机（装到主屏幕） | V1.1 | 公司内部工具：按空间走、逐条勾选、记一句话结论 |

三者是同一个产品的三种呈现：字段、规则、文案、判据完全一致，差异只在布局与动线。

### 1.2 V1 的技术范围

做：账号与角色、需求单导入与列表、原始表格视图、外发前逐条确认与脱敏、表格理解、清单生成、清单导出、外发审计记录、模型 adapter、契约层。

不做：现场记录与离线同步（V1.1）、采集端云端对接、分享链接、方案与报价、房主端沟通。

产品文档第九章列出的产品边界同样适用于本方案。

### 1.3 前提

以下五条是选型的输入，任何一条发生变化都要重新评估本方案（见第九章）：

1. 解读台是网页产品，不做小程序；手机端要按现场动线单独设计，不是把桌面页面缩窄。
2. 服务、数据与模型全部在境内，不允许出现「房主数据 → 境外服务」的路径。
3. 采集端最终会改为提交到云端。V1 的文件导入只是同一个接口的另一种输入方式，不是长期形态。
4. **本工具只服务自己公司**，不对外销售。因此它是单组织的内部系统：不做多租户、不做计费、不做对外注册。
5. 模型固定为 DeepSeek；换模型时只替换 adapter，上层不动。

## 二、技术选型

### 2.1 选型结论

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | TypeScript | 领域模型与判断逻辑在服务端和三端共用 |
| API 服务 | Node + Hono（备选 Fastify） | 类型契约好、Docker 部署简单；团队变大再考虑 NestJS |
| 数据库 | 境内托管 Postgres + Drizzle | 单组织，不做租户隔离；访问权限按角色控制 |
| 契约 | zod schema → 生成 OpenAPI，独立 `packages/contracts` | 三端共用一个契约源，变更由类型检查兜住 |
| 鉴权 | API 侧自签 token | 公司内部账号：手机号验证码或企业微信扫码；采集端走微信登录换 session |
| 桌面工作台 | Next.js（App Router）+ React | 分享页要服务端渲染，路由、鉴权、构建一体化 |
| 样式 | Tailwind + CSS 变量 | 桌面与现场两套壳共用基础样式 |
| 前端状态 | Zustand + TanStack Query | 服务端数据、缓存、离线同步各归各家 |
| 现场端 | 独立工程：Vite + React + PWA（service worker + IndexedDB） | 离线优先是它的主场；与桌面端共用领域包与契约，不共用构建 |
| 领域层 | `packages/*` 纯 TS 包 | 零框架依赖，服务端与三端共用 |
| 模型 | DeepSeek（官方 API） | 接口在领域层定义，实现在服务端；换模型只换 adapter |
| 对象存储 | 境内 OSS / COS | 导出件与将来的分享图 |
| 测试 | Vitest + Playwright | 领域包、API、两端界面三层 |
| 包管理 | pnpm workspace | 领域包与应用的唯一共享方式 |
| 部署 | Docker + 公司自己的服务器或境内云主机 | 不引入 K8s |

### 2.2 为什么是「一个服务 + 三个壳」

**采集端也要上云，后端就不能挂在任何一个客户端上。** 一旦小程序变成把需求单提交到云端，后端就成了三个客户端的公共依赖，藏在某个 Web 框架的 route handler 里会很难看。独立之后，谁接入都是调用同一组接口。

**模型调用和脱敏必须在服务端。** 密钥不能进浏览器，脱敏要发生在任何外发之前，这两件事已经决定了服务端是一等公民，而不是可以后补的东西。

**领域逻辑是纯 TS，三端与服务端共用。** 字段规格、规则命中、清单判据、脱敏替换全部是确定性的纯函数，放在包里之后，小程序、Web、服务端跑的是同一份判断依据——这是「三端行为不漂移」的唯一可靠做法。

### 2.3 为什么前端是两个工程

**只读与分享访问需要服务端渲染。** 产品文档下一版要做的分享链接，需要的是「一个不带登录态的只读页面」，这是服务端渲染的主场，纯静态 SPA 做起来别扭。

**现场端拆出去，是因为它的难点和桌面端不一样。** 桌面端要的是服务端渲染（分享页、鉴权中间件、一体化部署），现场端要的是离线优先（service worker + 本地库 + 重连同步）和单手可操作的轻界面。前者是 Next.js 的主场，后者是它的次要场景；塞进一个工程，只会让构建、缓存与离线策略互相迁就。

**拆开不等于各写一套逻辑。** 两端共享 `packages/*`（判据、合并、排序、脱敏）与 `contracts`（接口契约），呈现层各写各的。UI 组件不抽公共包：两端组件差异大、复用率低，硬抽反而增加成本；真正该共用的是设计 token（同一套配色与字号）。

**一体化部署省事。** 路由、鉴权中间件、构建、静态资源，一个工程里解决；自托管用 Docker 跑 `next start` 即可。

### 2.4 明确不选

**不做多租户。** 只服务自己公司，把租户维度做进数据模型和仓储层，是在为不存在的需求付长期成本。本章的简化结论直接来自这条定位。

**不用 Taro 承载解读台。** Taro 唯一的优势是一套代码产出小程序与 H5，这个前提已经不成立；宽屏桌面是它的次要场景，用它反而要额外处理 rem 适配与路由。

**不用纯静态 H5 直连模型。** 密钥会暴露在浏览器、CORS 要绕、脱敏无法保证。只有在「使用者自带 key 且接受风险」时才勉强成立，与产品形态冲突。

**不上 Electron / Tauri 做桌面壳。** 产品是网页端，桌面壳不在范围内；将来若有需求，把同一个 Web 工程打包即可，不影响本方案。

**不上微服务与 K8s。** 单体 API 服务足够支撑到这个体量，拆分会先带来运维成本而不是收益。

**不做境外模型与境外云。** 见 7.1。

### 2.5 唯一没有把握的地方

拆成两个工程之后，Next.js 的离线风险没有了，但**现场端的离线同步本身**仍是全篇最没把握的一块：断网时产生的记录怎么排队、重连后怎么合并、同一条目在两台设备上都改过怎么办。这一块要在 M4 开工前用真机验证：

1. 断网下连续记 20 条，重连后一条不少；
2. 切后台、杀掉进程再回来，未同步的记录还在；
3. 同一条目两端都改时，不出现「结论被覆盖成空」。

验证不过就退到最保守的做法：现场记录一律只追加、不合并，冲突时两条都留，由设计师回公司选一条。

## 三、架构分层

### 3.1 结构

```
┌──────────────────── 客户端 ────────────────────┐
│  采集端小程序 / H5（已有）                       │
│  解读台 · 桌面工作台                             │
│  解读台 · 现场 PWA（独立工程，V1.1）              │
└───────────────────────┬────────────────────────┘
                        │  契约层 packages/contracts（zod → OpenAPI）
┌───────────────────────▼────────────────────────┐
│  API 服务 services/api                          │
│  · 鉴权与角色                                    │
│  · 需求单 / 清单 / 记录 资源                      │
│  · 脱敏 → 模型调用 → 外发审计                     │
└───────────────────────┬────────────────────────┘
                        │
┌───────────────────────▼────────────────────────┐
│  领域层 packages/*（纯 TS，零框架依赖）           │
│  field-spec · rules · summary                   │
│  checklist（新增） · redact（新增）               │
└───────────────────────┬────────────────────────┘
                        │
          Postgres · 对象存储 · DeepSeek
```

**分层纪律**：领域层不 import 任何框架、不读环境变量、不产生副作用；API 服务不自己写业务判断，只做编排与持久化；客户端不算业务结论。这条纪律是「三端一致」能否成立的前提。

### 3.2 依赖方向

```
packages/*        不依赖任何东西
services/api      → packages/*
studio（桌面）      → packages/* + contracts
onsite（现场 PWA）  → packages/* + contracts
app（采集端）      → packages/*
```

反向依赖一律不允许：领域包里出现框架 import、或 API 服务里出现界面判断，都要立刻停下修边界。

### 3.3 目标仓库结构

```
装修需求采集助手/
  app/                  # 采集端（Taro：weapp + h5），已有
  studio/               # 解读台桌面工作台（Next.js）
  onsite/               # 现场端（Vite + React + PWA，独立工程）
  services/
    api/                # API 服务（多客户端共用）
  packages/
    field-spec/         # 已有：字段规格、表单模型与校验
    rules/              # 已有：规则引擎
    summary/            # 已有：需求摘要与清单文本
    data/               # 已有：仓储接口，扩展为服务端实现
    checklist/          # 新增：判据筛选、合并、排序、计数
    redact/             # 新增：字段级三级策略与自由文本替换
    contracts/          # 新增：API 契约与共享类型
    devtools/           # 已有
  tools/  docs/  tests/  demo/  mobile/  designer/
```

`designer/设计需求解读台_Demo_V0.1.html` 与它的冒烟测试保留，作为交互设计稿与回归参照。

## 四、关键设计

### 4.1 契约优先

API 的请求与响应由 `packages/contracts` 里的 zod schema 定义，运行时校验、TypeScript 类型、OpenAPI 文档都由这一份产生。三个客户端不各自维护类型，契约变更由编译与测试兜住。

### 4.2 账号与权限

单组织，没有租户表，只有用户与角色：

| 层 | 含义 |
| --- | --- |
| 身份 user | 一名公司内部人员（设计师或管理员），或在采集端提交的房主 |
| 角色 role | 管理员（管账号、管字段清单版本） / 设计师（导入、生成、导出） |

两点当前口径：

1. **房主不是用户。** 房主通过采集端的匿名会话提交需求单，不进入账号体系。
2. **同公司内默认可见。** V1 的数据默认全员可见、操作留痕（谁导入、谁生成、谁导出都记录在案）。若要求「只能看到自己负责的客户」，加一个 `owner_id` 过滤即可，不需要改结构——是否要这条见第十章待定项。

如果将来公司内部要按门店或分部划分，用一个可空的 `team_id` 表达即可，不必引入完整的租户体系。

### 4.3 数据模型（核心表）

| 表 | 要点 |
| --- | --- |
| `users` | 账号、角色（管理员 / 设计师）、可空 `team_id` |
| `demand_sheets` | `schema_version`、`payload`(jsonb)、`ai_marks`(jsonb)、`submitted_at`、`source`（文件导入 / 采集端提交）、`submitted_by` |
| `checklists` | `demand_sheet_id`、生成时间、所用模型、规则版本 |
| `checklist_items` | **uuid 主键**、空间、档位（必问 / 建议问）、来源（需求推导 / 通用核实）、问题、为什么问、现场要核实、关联字段 ID |
| `outbound_records` | 每次生成的外发字段清单、脱敏命中位置、时间、操作人 |
| `site_records` | V1.1：**客户端生成的 uuid**、条目的稳定标识（核实对象 + 主要来源字段，不带分组）、状态（已问 / 没问上）、一句话结论或原因、记录时间 |

两个约束值得单独说：

**清单条目用 uuid，不用自增主键。** 现场端会离线创建记录并引用清单条目，自增主键在离线场景下做不到稳定引用。

**清单与现场记录分表。** 清单是生成物（换模型、调判据都可以重新生成），现场记录是资产（是「清单有没有用」的唯一证据，也是回头调判据的数据源），不能被重新生成覆盖掉。

### 4.4 清单在服务端生成

产品文档 4.2 的四类来源分工不变，落地位置明确如下：

| 来源 | 谁做 | 在哪 |
| --- | --- | --- |
| 空缺的推荐项、答「不清楚」的项 | 规则 | `checklist` 包 |
| 字段之间的矛盾（预算与面积、工期与定制周期） | 规则 | `rules` 包，已有 |
| 从已填内容推导「要问什么、为什么问」 | 模型（DeepSeek） | 服务端 adapter |
| 16 项通用量房清单 | 现成资产 | `field-spec/survey-checklist.json`，需补 `related_fields` |

判据筛选（产品文档 4.3）、合并（4.4）、排序与计数（4.5）全部落在 `checklist` 包，是纯函数，可单测。去重键用「归属空间 + 核实对象」的结构化键，不用文字相似度。

模型只负责推导问题与依据，输出必须附字段 ID；指不到字段的只能标为「来自通用量房清单」。

**生成放在服务端的三个理由**：模型调用本来就必须在服务端；外发记录要求可审计可复现；三个客户端拿到同一份清单，不会因为各自计算而分叉。一次生成是一条完整流水线，失败时不落半成品清单。

### 4.5 脱敏与外发：顺序即安全

产品文档第七章说的「本地处理」，在服务端化之后含义变为**自有服务端**——因为现在的「本机」就是自己的服务器。安全边界没有变：房主数据不许离开自有系统去第三方模型。这也是要单独评估 DeepSeek 接入方式的原因（见 4.7 与 7.1）。

顺序不能颠倒：

```
客户端勾选要外发的字段（F3）
      ↓
服务端按需求单取数（含不勾选的字段，用于本地规则计算）
      ↓
redact 包执行脱敏：不外发字段整条剔除；可泛化字段本地降级；自由文本先替换
      ↓
写入外发审计记录（字段清单 + 脱敏命中位置 + 时间 + 操作人）
      ↓
调用 DeepSeek
      ↓
落库生成清单
```

三条硬约束：不外发字段不进任何请求；外发必须经设计师逐条确认；外发记录事后可查（对应产品文档 7.4）。

**策略是可配置的数据，不是代码常量。** `redact` 包把策略作为入参（纯函数，因此同一份需求单在不同策略下的结果都能单测）；默认策略集随代码发布并带版本号，公司按合规口径调整时只改策略数据。每次外发记录与当次生效的策略版本一起落库——否则审计还原不出当时的口径。

产品文档 7.1 的判断在这里依然成立，而且更重要：四类来源里前三类中一大半是确定性判断，由服务端规则算出来，根本不经过模型——这本身就是最有效的脱敏。

### 4.6 字段清单版本

字段清单 Excel 是唯一的人类编辑入口，构建脚本导出为 `packages/field-spec` 的 JSON，服务端与三端引用同一份。需求单带 `schema_version`，读入时按版本做一次规范化。

原则：**版本对不上时不静默丢弃。** 未知字段保留原值，在界面上标注「字段清单已更新」，让设计师看得见差异。这是产品文档待确认项 1 的技术答案。

### 4.7 模型接入（DeepSeek）

接口在领域层定义，实现在服务端：

```
provider.understand({ fields, task }) → {
  profile, demands, conflicts, toConfirm,      // 表格理解四块
  derivedItems: [{ question, why, onsiteChecks, relatedFieldIds }]
}
```

六点要求：

1. **用 JSON Output，不解析自由文本。** 官方 API 是 OpenAI 兼容的，用它的结构化输出模式，并在提示词里把返回结构与示例写清楚。
2. **返回后必须过 zod 校验，两道红线。** 结构不合法，或出现字段清单之外的 `fieldId`，一律判为失败；重试仍失败则降级为纯规则清单，并在该需求单上标明「模型部分未生成」。**宁可少，不可编。**
3. **测试用 fake provider**，生成流程的单测不依赖真实模型；真实模型的效果实测放在 M2。
4. **型号在 M2 实测后再定**（推理型号与非推理型号各跑一遍三个种子场景），倾向用非推理型号做结构化抽取：结构化输出支持更完整、延迟与成本更低。
5. **缓存两层。** 结果按「需求单 + 字段清单版本 + 勾选集合」缓存；同时把系统提示词与字段清单固定放在请求前缀，以命中官方的前缀缓存、压低重复调用成本。
6. **超时、重试与可中断。** 生成是一次长任务（产品文档的目标是单份 ≤ 5 分钟），界面要有进度与中断，失败可重试且不产生半成品。

### 4.8 桌面端与现场端的分工边界

允许分叉的地方只有三处：导航结构、清单呈现方式、输入方式。

| | 桌面工作台 | 现场流程（手机） |
| --- | --- | --- |
| 动线 | 导入 → 确认外发 → 看理解 → 筛清单 → 导出 | 按空间走 → 勾选已问 → 记一句话结论 |
| 导航 | 侧边步骤 | 按空间分组、一次一屏 |
| 输入 | 键盘、多列、可折叠 | 大触控目标、少打字、语音可后置 |

必须共享的：领域逻辑（`packages/*`）与接口契约（`contracts`）。状态层与 UI 组件各写各的——两个工程、两个运行环境，硬共用状态层反而互相牵制。

**判定信号**：一旦业务判断开始出现在两个工程各自的代码里，说明逻辑没有沉到包里，应当先停下来重构，而不是继续加分支。

## 五、工程原则：把逻辑放在能自动验证的地方

与采集端同一条原则，这里更重要，因为它要同时服务三个客户端。

小程序端没有稳定的自动化手段，必须靠人在开发者工具里看。所以判断逻辑不能留在界面里：权限判定、清单判据、合并去重、排序、脱敏替换、字段规范化和版本迁移、模型返回的校验与降级，全部做成纯函数放到包里，在 Node 里用 Vitest 跑。呈现层只做「读状态、渲染、派发事件」。

目标是让「无法自动验证的代码」占比尽可能低。

## 六、质量保障

### 6.1 三层测试

| 层 | 工具 | 覆盖 | 谁能跑 |
| --- | --- | --- | --- |
| 领域包 | Vitest | 判据筛选、合并去重、排序计数、脱敏替换、规则命中、字段规格与版本迁移、模型返回校验与降级 | AI 可独立跑 |
| API | Vitest + 真实 Postgres | 鉴权与角色、契约校验、清单流水线、外发审计 | AI 可独立跑 |
| 桌面工作台 | Playwright | 导入 → 确认 → 理解 → 清单 → 导出（宽屏） | AI 可独立跑 |
| 现场端 PWA | Playwright | 选单 → 逐空间问 → 记一笔 / 没问上 → 断网记录与重连同步；手机 viewport，用离线模式模拟断网 | AI 可独立跑 |
| 小程序端 | miniprogram-automator | 平台适配层 | 需要开发者工具，可能人工 |

### 6.2 必须守住的验证点

- 清单与规则引用的字段 ID 必须存在于字段清单（防止字段清单与规则漂移）；
- 外发 payload 中不出现标为「不外发」的字段值——**误发即失败**；
- 每条清单项可溯源：要么有字段 ID，要么标为来自通用量房清单——**编造即失败**；
- 模型返回中出现字段清单之外的 `fieldId` 时，生成必须失败并降级；
- 未授权访问不返回任何数据；
- 字段清单升级后，旧需求单仍可读；
- 控制台无错误。

### 6.3 已有资产

`tests/designer.smoke.mjs` 已经覆盖了需求单列表、原始表格、外发前确认（含脱敏）、表格理解、清单删减与撤销、导出——这六组断言几乎逐一对应 V1 的功能，实现时直接迁移写法。`tests/unit/*` 的字段规格、规则、摘要断言同理。

## 七、部署与合规

### 7.1 境内与数据边界

- 服务、数据库、对象存储与模型全部在境内，DeepSeek 官方 API 在国内可直接访问；
- 房主信息在采集端要做明确告知与同意；
- 每次外发 DeepSeek 都留档，满足「事后可查」；
- 密钥走环境变量，不进仓库、不进前端。

**房主数据发给第三方模型服务，在合规口径上属于委托处理。** 口径由公司定，产品侧两条路都留：官方 API 是最省事的默认；私有化部署 DeepSeek 的开源模型（权重可自部署）让数据完全不出内网，代价是 GPU 与运维成本。两者 API 形态一致，只换 adapter 实现，切换不动上层，所以不必现在锁死。

### 7.2 部署形态

Docker 镜像 + 公司自己的服务器或境内云主机 + 托管 Postgres + 对象存储。

这里有一个容易忽略的连带影响：**设计师要在量房现场用手机访问，就必然要走公网**，那就需要域名与 ICP 备案；如果接受只在公司内网使用，可以省掉备案，代价是现场端（V1.1）实际上用不了，只能导出纸质清单带出门。这一条见第十章待定项 4。

### 7.3 环境

开发、预发、生产三套环境，数据库与对象存储分开。字段清单 JSON 属于代码资产，随代码一起发布，不走环境变量。

## 九、风险与退路

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| 模型输出编造或不可溯源 | 单测或线上出现无字段 ID、或字段清单之外的 ID | 收紧提示与校验，失败重试，仍失败则降级为纯规则清单 |
| DeepSeek 高峰延迟或限流 | 单份解读耗时明显超过 5 分钟 | 超时与重试、生成异步化、结果缓存；必要时换型号 |
| 结构化输出不稳 | 返回结构不合法比例偏高 | 明确 JSON 模板与示例，扩大重试，保留规则兜底 |
| 数据外发口径收紧 | 公司要求房主数据不出内网 | 私有化部署 DeepSeek 开源模型，只换 adapter |
| 两个前端工程的维护成本 | 同一处改动要在两个工程各改一遍 | 逻辑继续沉在 `packages/*`，两个工程的呈现层都只做渲染；跨端一致的行为由领域包的单测兜住 |
| 一个人维护三端 | 一处改动需要同步三处 | 继续把逻辑下沉到 `packages/*`；呈现层只留渲染 |
| 清单变长导致设计师大量删减 | 清单可用率低于目标 | 回去调判据，不设条数上限（产品文档 4.5 已定） |
| 调用成本超预期 | 单份解读调用次数或 token 过高 | 缓存 + 稳定前缀；只在字段或勾选集合变化时重新生成 |
| 依赖框架导致返工 | 领域包出现框架 import | 立即停下修边界，这是分层的底线 |

退路始终有效，因为领域包与框架无关——这是把它抽出来的主要目的。
