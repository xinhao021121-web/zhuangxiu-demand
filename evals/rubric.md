# 清单质量评估 · 评分标准

这份评估回答一个问题：**「把需求单变成量房沟通清单」这一步做得好不好。**

它的核心判断是——先把「能自动判的」和「必须人判的」分开。分不开，评估就会变成一句
「感觉还行」，也就没法在每次改动后复用。

| | 谁判 | 在哪 | 什么时候跑 |
| --- | --- | --- | --- |
| 可溯源、重复、降级、期望覆盖 | 代码 | `packages/service/src/eval.ts` | 每次提交（离线回归） |
| 「这条问得有没有价值」 | 人 | 本文第三节的评审表 | 每次改提示词或换型号 |

---

## 一、怎么跑

| 命令 | 跑什么 | 判不判通过 |
| --- | --- | --- |
| `pnpm run test:unit` | 3 个种子场景（录制输出），回归门禁 | **判**：本文第二节所有判死项必须为 0 |
| `pnpm run eval:model` | 13 个用例 × 3 次采样，真机实测（需 `DEEPSEEK_API_KEY`） | **不判**：只出覆盖率与稳定性报告，阈值等基线 |

报告落在 `evals/report-offline.md`（每次跑离线回归都刷新，不带时间戳，重跑不改文件，
可以直接当基线提交）与 `evals/report-model.md`（只有跑真机实测才生成）。

**真机实测为什么不设通过阈值**：产品文档 7.5 已经定了「阈值先取基线，不拍数字」。
拿一个拍出来的通过线去卡真机结果，只会让人为了过线去调指标。真机的用途是让问题可见：
哪些用例没覆盖、哪几条飘、飘在哪个分区。

## 二、自动判的部分

### 判死项（必须为 0，否则离线回归不通过）

| 指标 | 口径 | 为什么这么定 |
| --- | --- | --- |
| 可溯源（`untraceable`） | 清单里来源不是通用资产的条目，`relatedFields` 不能为空 | 产品文档 5.7 的硬约束：指不到字段的不许出现。这条是「不编造」的可执行版本 |
| 同对象重复（`duplicates`） | 同一「分区 + 核实对象」不能出两条 | 合并键就是这两项，出了两条说明合并失效，设计师会看到两份半截信息 |
| 降级（`degraded`） | 模型两道红线没过、重试仍失败时为真 | 降级意味着这份清单少了针对这家的推导项。离线固定桩下不该出现；真机出现要按原因归因（结构 / 越界字段 / 超时 / 截断） |
| 期望覆盖（`missingFields` / `missingObjects` / `missingMerges`） | 用例声明的期望必须全部命中 | 这是「接住了这家人」的最小证据，见第四节 |
| 新对象上限（`maxNovelObjects`） | 只有写了这条的用例才判 | 抓「硬凑条数」：信息很少的需求单不该冒出一堆通用清单之外的问题 |

### 只报数、不判死

| 观测项 | 为什么只看数 |
| --- | --- |
| 条目数 / 必问数 / 建议问数 | 产品文档 5.6 明确不设条数上限，用条数卡会砍掉真问题。阈值要等设计师删减数据 |
| 通用清单之外的新核实对象（`novelObjects`） | 这是模型真读懂了才有的东西（如「猫砂盆位置」）。太少说明只会念通用清单，太多说明在堆量——两头都不对，所以只报数 |
| 同对象跨分区（`multiSpaceObjects`） | 多数是合法的实例拆分（主卫 / 次卫各问一次）。分区漂移现在已被代码挡住（技术方案 6.7 的「分区以资产为准」），留这个观测项是为了它复发时看得见 |
| 房主暴露的不确定项接住率 | 现状是 0，但原因在口径不在模型，见第六节 |

## 三、必须人判的部分

自动指标能判「有没有」，判不了「好不好」。一条清单项要过这四关，只能人看：

| # | 维度 | 合格的样子 | 不合格的样子 |
| --- | --- | --- | --- |
| 1 | 是问题，不是结论 | 「厨房是否接受开放式」 | 「建议做开放式厨房」 |
| 2 | 依据成立 | 依据真的来自这份需求单的填写 | 依据是通用常识，换成任何一家都成立 |
| 3 | 现场要核实具体 | 判了「影响可行性」的，必须说得出到现场核实什么 | 只说「现场条件可能不允许」，说不出核实点 |
| 4 | 档位对得上 | 必问 = 不问就会做错、要返工 | 把「提醒一下更好」也算成必问 |

**抽样规则**：每个用例抽前 5 条必问 + 前 3 条建议问。三个种子场景全量评。

**判定**：每条给 `合格 / 待改 / 错误` 三档；给「错误」的必须写下原因，进 `badcases.md`。

**一致率**：有第二个人就做双评，算简单一致率与分歧条目；只有一个人评时，
报告里标「单评」——不把单评说成一致率。

## 四、期望怎么标（这份评估最容易做错的地方）

期望只写**「房主已经暴露、清单必须接住什么」**，不写「模型该输出什么」。
用例里的每一条期望都能追到它改了哪个字段；追不到的期望不许写——
否则测的只是「模型和它自己一致」。

| 期望字段 | 含义 | 例 |
| --- | --- | --- |
| `coverFields` | 清单里必须有条目指到这些字段键 | 用例把 `kt_form` 改成「开放式」，清单就必须有条目指到它 |
| `coverObjects` | 清单里必须出现这些核实对象 | 养猫 → 必须出现「猫砂盆位置」 |
| `mergeObjects` | 这些对象必须与通用清单**合并成一条**（来源为两者） | 开放式厨房 + 高频下厨 → 不是只出通用提醒，而是并成带这份需求依据的一条 |
| `maxNovelObjects` | 通用清单之外的新对象上限 | 空需求单：上限 0 |

## 五、用例怎么扩

现在 13 个：3 个种子（`recorded: true`，有录制输出，进离线回归）+ 10 个边界用例
（`recorded: false`，只跑真机）。

扩用例的方式是在种子上做**变异**，不是从零写一份 191 字段的需求单：

1. 想清楚要考什么（一句话，写进 `intent`）；
2. 只改能体现这个考点的几个字段；
3. 期望跟着改的字段走；
4. 边界场景优先补这几类：房主信息极少、房主答「不清楚」、互相矛盾的需求、
   实例字段（主卫 / 次卫 / 次卧）、极端预算与工期。

## 六、这次离线跑出来的两个口径差异

离线回归跑出了「房主暴露的不确定项 0/10 接住」。拆开看是两件性质不同的事：

| 现象 | 性质 | 为什么 | 怎么处理 |
| --- | --- | --- | --- |
| 房主答「不清楚」的项没进清单 | **缺陷** | 产品文档 5.3 写明这类答案是「量房时最该聊的」，但实现里它只进表格理解的待确认项 | 进 `badcases.md`，模型侧或实现侧二选一补上 |
| 空缺的推荐填写项没进清单 | **口径差异** | 设计上它属于「待确认项」，设计师在表格理解里看得到，只是不进清单、也不会被现场端逐条问 | 需要产品决定：是接受这个分工，还是让关键的空缺项也进清单 |

第一件事的现场证据：`d1` 里房主对**新风系统**选了「不确定」——等于当面说「你来定」——
而清单里没有任何一条提到它。这不是文案问题，是漏了一次真正的量房沟通。

## 七、这份评估不测什么

说清楚边界，比让人以为它面面俱到要好：

- **不测模型耗时与成本**——那是 `pnpm run measure:model` 的口径（型号对比、降级原因）。
- **不测清单长度是否合适**——阈值未定，现在只报数。
- **不测界面与现场端**——那是 `tests/*.e2e.mjs` 的端到端与演示冒烟。
- **不测房主端的发现引擎**——那是确定性规则，由 `tests/unit/rules.test.ts` 覆盖，不经过模型。
- **不测「覆盖了多少真实房主会遇到的问题」**——现在用的是种子与变异用例，不是真实需求单。
  等采集端上线、有了真实数据，用例集要从真实需求单里补。
