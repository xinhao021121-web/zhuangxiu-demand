# 清单质量 badcase 台账

每一条记录 = 一个被看见的问题 + 一个归类 + 一个处理决定。

为什么必须有台账：产品文档 7.5 定了「阈值先取基线，不拍数字」，那么在没有阈值的情况下，
判断「这次结果变好还是变坏」靠的就是这张表。没有它，同一类问题会在每次换型号、改提示词时
重新出现一次，而没人认领。

| 列 | 说明 |
| --- | --- |
| 编号 | `BC-序号`，不复用 |
| 发现于 | 离线回归 / 真机实测 / 人评 |
| 用例 | 哪个用例，没有对应用例就先补一个 |
| 现象 | 写现象，不写猜测 |
| 归类 | **模型**（提示词或型号的问题）/ **口径**（文档与实现不一致）/ **实现**（代码问题） |
| 影响 | 这个现象会让设计师在现场漏掉什么 |
| 处理决定 | 改什么、谁改；没定就写「待定」 |
| 状态 | 待定 / 已修复 / 不接受 |

归类很重要：**口径问题不要用改提示词去补**。那会让模型去猜一个产品文档自己都没定的事，
这次猜对了，下次换个型号又错了。

## 台账

| 编号 | 发现于 | 用例 | 现象 | 归类 | 影响 | 处理决定 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| BC-01 | 离线回归 | `d1` | 房主对「新风系统」选了「不确定」，清单里没有任何一条提到它 | 实现 | 房主当面说了「你来定」，现场却没人问这一条 | **已修复**：`unclearCandidates` 把答「不清楚」的项变成清单候选——能落到通用清单的并成一条，落不到的用 `field-spec` 新资产 `unclear-checklist.json`（9 个带该选项的字段里 6 个需要单独配，另外 3 个已被通用清单覆盖）。证据：`d1` 的接住率从 0/4 变成 1/4，`evals/cases.ts` 的 `d1` 用例已加 `dev_freshair` 作回归门禁 | 已修复 |
| BC-02 | 离线回归 | `d1` / `d2` / `d3` | 空缺的推荐填写项不在清单里，只出现在表格理解的待确认项 | 口径 | 设计师在表格理解里看得到，但现场端不会逐条问 | 待产品决定：接受这个分工，还是让关键空缺项也进清单 | 待定 |

> 这两条都出自第一次离线回归的观测项「房主暴露的不确定项 0/10 接住」。
> 一个偏实现（该进没进，已修），一个偏口径（设计上就没打算进，仍待决定）。放在一起才看得出区别。

## 新增一条时照着填

表头与格式示例如下（示例行不要留在台账里，换成真实发现）：

```
| BC-03 | 真机实测 | b1-open-kitchen | 排烟出了两条，一条归「厨房」、一条归「基本信息」 | 模型 | 同一件事在清单里出现两次，设计师要自己判断哪条作废 | 若复发，在代码里做核实对象名归一，不靠提示词自觉 | 待定 |
```

## 处理流程（与产品文档 7.4 对齐）

1. **汇总**：离线回归或真机实测跑出报告，把未通过项与观测项异常逐条抄进台账；
2. **判断**：是模型、口径还是实现？口径问题回到产品文档改定义，不要用提示词盖过去；
3. **改动**：一次改动 = 一次提交 + 一次种子场景回归（`pnpm run test:unit` 会跑）；
4. **验证**：改动后重跑，看这条现象是否消失、有没有连带弄坏别的用例；然后回来更新状态。
