# 清单质量 badcase 台账

每一条记录 = 一个被看见的问题 + 一个归类 + 一个处理决定。

为什么必须有台账：产品文档 7.5 定了「阈值先取基线，不拍数字」，那么在没有阈值的情况下，
判断「这次结果变好还是变坏」靠的就是这张表。没有它，同一类问题会在每次换型号、改提示词时
重新出现一次，而没人认领。

| 列 | 说明 |
| --- | --- |
| 编号 | `BC-序号`，不复用 |
| 发现于 | 离线回归 / 真机实测 / 人评 |
| 用例 | 哪个用例，没有对应用例就先补一个 |
| 现象 | 写现象，不写猜测 |
| 归类 | **模型**（提示词或型号的问题）/ **口径**（文档与实现不一致）/ **实现**（代码问题） |
| 影响 | 这个现象会让设计师在现场漏掉什么 |
| 处理决定 | 改什么、谁改；没定就写「待定」 |
| 状态 | 待定 / 已修复 / 不接受 |

归类很重要：**口径问题不要用改提示词去补**。那会让模型去猜一个产品文档自己都没定的事，
这次猜对了，下次换个型号又错了。

## 新增一条时照着填

表头与格式示例如下（示例行不要留在台账里，换成真实发现）：

```
| BC-XX | 真机实测 | b1-open-kitchen | 排烟出了两条，一条归「厨房」、一条归「基本信息」 | 模型 | 同一件事在清单里出现两次，设计师要自己判断哪条作废 | 若复发，在代码里做核实对象名归一，不靠提示词自觉 | 待定 |
```

## 处理流程（与产品文档 7.4 对齐）

1. **汇总**：离线回归或真机实测跑出报告，把未通过项与观测项异常逐条抄进台账；
2. **判断**：是模型、口径还是实现？口径问题回到产品文档改定义，不要用提示词盖过去；
3. **改动**：一次改动 = 一次提交 + 一次种子场景回归（`pnpm run test:unit` 会跑）；
4. **验证**：改动后重跑，看这条现象是否消失、有没有连带弄坏别的用例；然后回来更新状态。
